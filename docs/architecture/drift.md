# Drift detector

Status: PR 1 implemented; PR 2 pure parts implemented (`drift-rules.ts`, `drift-eval.ts`, no flag writer yet) (the pure episode detector, `GET /api/drift-report`, `rhen drift report`); PR 3a-1 implemented (the `drift` activity source, inferred work labels with the owner's one-tap correction); PR 3-1 implemented (the owner-only `drift-reason` source and the reason box in the deviated sheet; tags, their correction card and the prompt gate are not built); the flag tick, shift-end measurement and report extension are deferred until live data exists; activity mismatch is held back, see "Held back". Owns: what counts as one drift, how its time and its pinning are decided, and the read route that reports episodes (`platform/contracts/src/drift/`, `portal/server/drift/`).

A drift is a moment the person stopped doing what the plan sanctioned. The detector turns stored rows into **episodes**, one per drift however many signals saw it, so a later measure of "did we see it coming" counts drifts and not signals. It only measures. Nothing under `engine/`, `now-activity.ts`, the planning contracts or `plan-input-tables.json` imports or reads it (`drift-boundary.test.ts`), so a detection never reorders what the plan offers. It sets nothing, sends nothing and has no switch.

## Episodes

| Type | Defined by | Never counted |
|---|---|---|
| `deviated_checkin` | a check-in answered `deviated` by the person, outside any running session | silence (an unanswered check-in), `disrupted`, `alternative` sessions, answers by an agent, answers with source `session_reconciliation` |
| `unsanctioned_session` | a session that started with no plan sanction | a `planned` session that never started, sessions created before the legacy cut |

- **One episode per drift.** A session that later ends, or switches to another off-plan item, is extra evidence on its start (`session_ended`), not a second event. A deviated answer within 10 minutes before the session starts or after it ends joins that session's episode. The primary type is `unsanctioned_session` when both are present. Counts are of episodes per primary type; per-signal counts sit beside them.
- **Times.** `occurredAt` is when the drift happened. `knownAt` is when the system first knew: `startedRecordedAt` or `endedRecordedAt` when a reconciled session was recorded later than its time, else `occurredAt`.
- **Pinned.** An episode is pinned when `occurredAt` was recorded live: an unsanctioned session whose `knownAt` is within 2 minutes of its start. A deviated check-in is never pinned, because its time is when it was answered. **Only pinned episodes may count toward lead-time recall or the go/no-go count.**
- **Unsanctioned means no sanction at start.** `sessions.plan_sanction` is null when the target was unsanctioned at start, and also on a session older than the column. The judge's `unsanctioned` reason is not stored (pulse segments keep `lapsed`, not the judge's reason), so the detector reads the column. `legacyBefore` (`?legacyBefore=` on the route, `--legacy-before` on the CLI) skips sessions created before that time; without it every null counts, which overcounts on a database that holds old rows. Sessions an agent started with a null sanction count as the person's drift too (`started_by` is not read yet). When a table hits its row cap the newest rows are kept and the oldest dropped.
- **Deviated check-ins** are skipped inside a running session, where the evidence is the session itself.

## The read route

`GET /api/drift-report` (scope `read:plan`, hand-added in `mcp-route-table.ts`, entry `rest-drift-report` in the data-flow registry as a pass-through read) returns `{ generatedAt, window, legacyBefore, truncated, counts, episodes }`. It reads `check_in` and `sessions` only, never the activity store, and is bounded two ways: by time (`?days=`, default 30, at most 90, or `?from=` and `?to=` for a window of at most 90 days; rows are widened by the 10-minute collapse window only) and by rows (5,000 per table; `truncated` says a table hit it). Without `DATABASE_URL` it answers 503 and names the next call; an unreadable time or a window over 90 days answers 400.

`rhen drift report [--days n] [--from iso] [--to iso] [--legacy-before iso] [--json]` prints it. The command is `ownerOnly`, so it is not an MCP tool and the tool count is unchanged (`tools/cli/test/mcp.test.ts` pins it). The module is imported through `@openrhen/contracts/drift` and deliberately not re-exported from the contracts barrel.

## Held back: activity mismatch

The plan's third type, foreground activity that does not fit the planned item, needs to know whether the planned item is "work". No stored field said so when this was written (work labels now exist, below, but the type stays held back until the flag writer wires them): `actions`, `commitments`, `projects` and `outcomes` carry no work or leisure class, `areas` has only a free-text `name`, and `deviation_category` classifies what the person did instead. Reading a name such as "Work" would be a guess, so the type is not built and is recorded as an escalation. When an owner-editable field exists, the type returns with its category table (`games` and `game` folded, unmapped meaning unknown, never a mismatch), and with rules that idle, lock, display-off, pause and capture gaps break an interval and never count, that liveness comes from `heartbeat` and `coverage` rows, and that applied corrections (`attrs.corrects`) are honoured first.

## Shadow rules and the evaluation (PR 2, pure parts)

`drift-rules.ts` holds two baseline rules, run in shadow (a flag sends nothing). Rule B flags the first 30 minutes after a shift end that the caller measured from activity (not pulse's shift-grace lapse). Rule A, a hidden denylist interval or a game/media foreground during a work item, is a pure function over an injected `isWorkItem` predicate; with none wired it never fires. The marker now exists as inferred work labels (below), but nothing wires them into a tick until the flag writer is built. Thresholds live in one frozen object. A moment is eligible when pulse is `on`, capture is live, and it is at least 5 minutes after a switch; each rule has a 15-minute cooldown and a 5-minute flag bucket for the idempotent key `user|rule|bucket`.

A rule is scored only on drift types whose definition shares none of its signals (`labelSignals`, `ruleSignals`; rule A is never scored on activity mismatch). Features may not touch pulse-state internals; `drift-features.test.ts` walks the import graph to prove it.

`drift-eval.ts` scores flags: a hit is a pinned episode of a scorable type starting 2 to 5 minutes after the flag; a false alarm is a flag with none; rates are per waking day (capture-off days reported apart). Intervals come from a day-resampled bootstrap with a fixed seed and a fixed threshold; below 30 scorable pinned drifts in the scored subset the result is "not testable". The report prints the drifts lost to the 5-minute post-switch window, compares with random flags at the same alarm budget, and records the 20% holdout hash assignment without using it to subset. A chronological split with a one-horizon embargo is available for threshold tuning.

Not built: the flag writer (kind `flag` is registered, and its validator refuses a forged one, but nothing writes it), its registry entry and probe, shift-end measurement, and the report extension. They wait for live data: `rhen-watch` writes a row only when an interval closes, an idle interval is known only after input resumes, heartbeats are hourly and the uploader is not built, so a live tick could not see what rule A and B need. Until then a shadow evaluation can only be a replay over closed intervals, labelled as a replay and never as a live prediction.

## Work labels (PR 3a-1)

Rule A needs to know whether the planned item is work. The owner chose to infer it: the system reads an area's name and the titles of its open outcomes, projects and actions with the local model (tier `t2`, `portal/server/drift/work-label-runner.ts`), shows the answer, and the owner corrects it with one tap. The unit is the area; a leisure action inside a work area counts as work, and an item with no area is unknown.

- **What the model sees.** Only public plan text: the area's name and description, and titles of open outcomes, projects and actions, at most 40 titles and 2 KB. A private area is dropped whole; a private project, a private action, an action under a private project, and anything closed or archived are dropped before the prompt is built (`buildAreaSnapshots`, tested with a private project under a public area) and so never reach the stored `evidence`. The text is fenced as untrusted data after a fixed instruction block (`WORK_LABEL_PROMPT_VERSION`, pinned by a golden test). The reply is strict JSON `{label, evidence}`; a refusal reads as a fixed sentence and never echoes the reply. A private area stays unknown to the model, though the owner may answer for it. Area text is a new class of data sent to the same local host as mail text; it goes nowhere else, is never logged, and the job's answer carries only a status, a flag and at most one area id.
- **The job.** The `work-label-tick` worker loop posts `POST /api/integrations/work-label/tick`: one area per run so the shared local-model queue is held for one call at a time. Under the activity lock it picks an area with no label for its current text, prompt version and model, and hashes the exact text it will send; with no lock it calls the model; under the lock again it stores the row only if the area is still public and its text still hashes the same, else the answer is dropped. An area the owner has answered is not asked about. With no `t2` model set it answers `not_configured` and the owner can label by hand. There is no switch.
- **Resolution** (`resolveWorkLabels`, pure). Per area: the owner's latest `corrected` row wins whenever it was given and `unset` retracts it; otherwise the latest `inferred` row whose `input_hash` and `prompt_version` equal the area's text now (so a text that goes A, B, A reads A's label again, and an edit leaves the area unknown until it is labelled again); otherwise unknown, which is never work. Rows order by start time, then arrival time, then id. Rows from another writer are ignored (see [Activity store](activity-store.md) "Drift rows"). `workItemPredicate` turns the resolved labels and an item-to-area lookup into the `isWorkItem` that `workItemDiversionApplies` takes: true only for an item whose area is work. Nothing calls it yet; the flag writer will.
- **Correction.** The area page shows "Counts as work: Yes (inferred)", "No (your answer)" or "Not decided yet", with Yes, No and Reset. A tap is `PUT /api/work-labels/[areaId]` `{label, requestId}` (owner only, no MCP tool; the request id makes a retried tap one row) and `GET /api/work-labels` lists them. A correction survives a rewrite of the area's text, because it is the owner's answer; Reset hands the area back to the model.

## Check-in words and tags

A check-in answer carries the owner's own words (`deviationNote`) on every status, not only `deviated`, up to 8000 characters; a reconciliation answer keeps them for its tail only, never the on-track trunk. No status is added and the pulse judge is unchanged: the status is always the owner's yes, no or not sure. `deviationCategory` is still accepted from older callers (deviated answers only) and stored, but no surface in this repository asks for it. `answerSource` is `in_app_banner`, `sheet`, `push_action`, `widget`, `shortcut`, `app` or `session_reconciliation` (a voluntary check-in cannot be the last).

`check_in.tags` (migration 0153) holds open tags on those words: `[{tag, mark}]`, where `mark` is `stated` (the owner named it) or `inferred` (a reader took it from his words, so he sees it and can remove it). A tag is a lower-cased, trimmed, NFC-composed phrase of 1 to 40 characters with no control character, 12 at most per check-in. A reader writes them with `tag_check_in` (`rhen check-in-tag`, `rhen_check_in_tag`, scope `write:check-in`, same route as the answer): it adds or removes tags on an already-answered check-in and touches nothing else, so it never counts as contact and never changes the pulse. `stated` replaces `inferred` for the same tag, never the reverse; a command that changes nothing leaves the version alone. A reader finds the ids to tag with `GET /api/check-ins/answered` (`rhen check-ins`, scope `read:plan`): answered check-ins only, oldest answer first, each in the stored shape with its `version`, words and `tags`; `?untagged=1` keeps those with no tag, `?with-words=1` those with non-blank words, `?limit=` is 1 to 200 (default 50), and `next` in the result, passed back as `?after=`, pages on (null at the end; the cursor holds the answer time to the microsecond and the id, so no row repeats or is skipped). Any parameter it cannot read is a 400 that says what to send. The tags are separate from the "What pulled you off?" tags below, which belong to the private `drift-reason` source, and the two stay two stores on purpose: the drift-reason source is owner-only with no token access by design (the private "why" words), while check-in tags must be read and written by a reader holding a token (`read:plan`, `write:check-in`), so one store would either expose the private reason tags or lock the reader out.

## "What pulled you off?" (PR 3-1)

The deviated sheet in the check-in banner has an optional text box above the Note. The Note, labelled "In your words", still means what the person did instead (`deviationNote`, up to 8000 characters, kept on any answer; the sheet no longer asks for a category); the box is a different thing and is never written to the check-in or sent through `answer_check_in`, which agents and the CLI also call, so no agent can put words in the owner's mouth. There are no chips and no select for it: a fixed list of reasons would be a preset the person has to fit into.

- **Save path.** After the disruption and the answer are saved, a non-empty box is saved by `POST /api/drift-reasons` `{checkInId, text, requestId}` (owner only, no MCP tool, listed in the owner table of `agent-routes.ts`), and only then does the sheet close. If the save fails, the check-in stays answered and the sheet stays open with the typed words, the sentence ("Could not reach the portal. Try again." for a network failure, the portal's own sentence otherwise), Try again and Skip. A retry of the same words reuses the request id, so it is one row; different words get a new id. The sheet closes only after the reason is saved or skipped.
- **Server checks**, inside the activity lock: the check-in is the person's, `deviated`, answered by the owner (`answered_by` is null) and not by session reconciliation; the words pass the limit (1000 characters and 3500 UTF-8 bytes, so a box of emoji is refused readably rather than failing the row); a reused request id carrying other words is a 409. The answer is `{id, created}`, never the words. A later save for the same check-in is a new row and the latest wins, by the time the server stored it and then by row id (`resolveReasons`); earlier saves stay until the owner deletes the reason. "Owner" here is the absence of an agent header, a label and not a credential, so the guarantee against a headerless caller is `OPENRHEN_OWNER_AUTH=require`, the same as every owner route.
- **Privacy.** The words live in their own source, `drift-reason` ([Activity store](activity-store.md), "Reason rows"): no token can read or write it, no generic listing shows it, retention never applies, and `DELETE /api/drift-reasons/[checkInId]` removes a reason, its earlier saves and its tags. No log line, error message or receipt holds the words, and no module outside the reason store and service names the source (a test walks the portal). Reasons and tags are known only after the drift, so they are never a feature of a rule or of the evaluation: the rule, evaluation, episode and label modules reach no reason module (an import-closure test).
- **Not built here.** The tag writer, the correction card and the prompt gate. `reason_tag` is registered with its validator so the shape is fixed, but nothing writes it. The prompt gate waits until something writes prompt rows. An ask inside the sheet the person opened is not a predictor prompt, so it spends none of the prompt budget research §11.7 describes; the budget gates standalone prompts only, which do not exist yet.
