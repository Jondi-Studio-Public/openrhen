# Reconcile replay harness

Status: core harness and seeded generator implemented (40 golden cases, generated suites at three plan sizes, scoring, two baselines). Owns: the replay harness in `platform/contracts/src/planning/replay/`, its fixtures in `platform/contracts/test/replay/`, and the `Reconciler` interface.

The replay harness scores what happens after a message has been read into facts: does it change the plan, restate something already on it, raise a question, do nothing, or fail to resolve. It runs in memory with no database or network, inside the contracts unit run.

## The unit under test

`Reconciler = (input, { chooser }) => outcome`. The input is a plan (commitments, actions and projects with deadlines, contacts, remembered aliases, open asks) and one message with at most one fact. The outcome is one of five end states: `applied` (a create, update or cancel, with a target), `duplicate` (it restates a record), `asked` (held for a question), `no_effect` (with a reason) or `unresolved` (with a reason). It also carries up to five `candidates` (id, rank, score, lane), a `tie` flag, `usedChooser` and the chooser's pick. `replay-reference.ts` is today's behaviour behind that interface, which asks on equal matches (the matcher's tie result) and reads a deadline the same title names within two weeks of another date as that deadline moved (an update); the real reconciler replaces it without touching the cases or the scoring.

A chooser sees a quote and at most five cards and answers `cN`, `none` or `unsure`. Every case runs on the deterministic path (a chooser that must not be called) and on three stub paths: `oracle`, `adversarial` and `noisy`. A real model never runs in CI.

## Cases and privacy

`golden.json` holds hand-written cases: an `id`, `tags`, the `input`, and a `gold` (end state, target, acceptable targets, op, reason, `mustNot`, `deny`). Names are fictional, addresses are `@example.test`, and the source is `message-test`. `lexicon.json` lists the only words a title, quote or name may use; the guard test fails on any other word, any other address, or secret-shaped text, so a pasted real message cannot merge. The guard is fail-closed: any other string field must look like an id, timestamp, address or enum value, so a new prose field is flagged until the guard is taught it, and a `note` is capped at 200 characters. A second set of tests runs it backwards, planting a real-looking title, quote, sender, display name, note, conversation key and reason into every committed case and requiring a finding. Add a word to the lexicon only for a neutral one.

A labelled set kept outside git (reviewed real cases) uses the same case format. `scripts/test/replay-case-files.mjs` reads a directory of `*.json` files (nothing when it is unset or missing; a directory inside a git checkout is refused) and `parseExternalCases` turns them into cases, so such a set needs no code change. Paths are resolved first, so a symlinked directory or file that points into a checkout is refused too. The committed suite does not depend on it.

## The seeded generator

`replay-generate.ts` builds a plan from a fixed fake vocabulary (words in `lexicon.json`, contacts at `example.test`) and derives each message from a plan record by one mutation, so the gold comes from the mutation and nothing is labelled. The 1x plan has about 411 records; 5x and 20x multiply the commitments, actions, projects and asks, not the contacts. The kinds are a restated or reworded event, a move, a cancellation (of a real, an unknown and a look-alike title), a new event, a past one, a message with no facts or no start time, a remembered alias, twin records, twins told apart by sender, a recurring neighbour, and for deadlines and asks the same, moved, new, numbered, twin and same-thread variants, and a deadline neighbour (the same unnumbered title a week from one on the plan, gold a new deadline), which records how often the 14-day moved window merges two instances. The seed is fixed in the test (`DEFAULT_SEED`); plans and messages draw from separate streams, so asking for more cases never changes the plan or the cases before them. Each plan is built once, frozen and shared by its cases, so a runner copies only the message.

The CI run is 1,000 cases at 1x, 150 at 5x and 100 at 20x (about four seconds); cases are measured per kind, per tag and per size. `REPLAY_LARGE=1` runs about 18,600 cases and `REPLAY_SEED` changes the seed, both for a local sweep that checks the hard invariants and prints the figures (see the comment at the bottom of `replay-suite.test.ts`). On the chooser paths only the cases that ended `asked` are rerun, since no other case could have used a judge; a test holds that equal to running everything on the golden suite.

## Scoring and the baseline

Scores are overall, per tag and per plan size: a confusion matrix over end states, applied precision, false-merge, wrong-create and wrong-duplicate rates, Deny rate and Confirm accuracy, tie rate and tie resolution, recall at five, the share resolved without a chooser, questions per 100 messages and the unresolved share, each with a count pair that a Wilson interval can be drawn from.

`baseline.json` (golden) and `baseline-generated.json` (generated, with its seed and counts) are the last accepted results. The suite fails when applied precision, recall at five or the no-chooser share falls, and when any recorded figure differs, so a change of behaviour always shows in the baseline diff; a deliberate change updates the baseline in the same commit with the reason in the message. Two invariants are never ratcheted: nothing resolves to one target on a tied top rank without a chooser, and nothing does what a case's `mustNot` forbids. The baseline lists the cases that break them today (the tie list is empty; the rest are moved events read as new); those lists may only shrink. The no-chooser share dropped when ties stopped being guessed (a guess counted as resolved), and the contact map should win part of it back. A third list, `adversarialNewWrongDuplicates`, holds the cases where an adversarial chooser pins a restatement to the wrong record; a weak judge can do that, so it is tracked rather than forbidden, and it too may only shrink. In the generated baseline the lists hold case ids, which carry the size and position.

## Tie result

`matchCommitment` no longer lets the first of several equal matches win. A tie keeps the best `kind` and adds `tie: true` and `candidates` (at most five ids, earliest start first, then id, so the answer does not depend on input order); `commitmentId` is the earliest tied one, a stable stand-in so a reader of one id does not break. Core callers treat a tie as a question: an import holds a possible "Same event / Keep both" on the earliest, with the reason "Two commitments fit equally", and never links; the editor's notice reports it as possible. `matchSeriesToRule` is unchanged. The reference resolver asks on any tie and does not consult a chooser, since a pick between equals is a guess code cannot re-validate.

The Priorities repin that brings this in must also change the overlay readers of the matcher, because a tie still carries a `commitmentId`: the mail validator's timed-commitment match returns the matched title for any non-`none` kind, so a tie would be reported as a duplicate of the earliest commitment; it should return a tie as its own result (the titles of `candidates`) and ask which one, never create or merge. The mail ingest's duplicate finder reports a strong tie as a strong match; it should report `possible` when `match.tie` is set. Each gets a test with two equal commitments.

## Deadline and ask matching

`matchDeadline` (`deadline-match.ts`) matches a deadline or an undated ask against pure target rows (open actions, deliverables, projects with an external deadline, open ask facts). A unit code that exactly one target names is exact. The same title on the same date is strong; on a date up to 14 days apart it is strong with `moved: {from, to}` (an update, not a duplicate); except that the same unnumbered title a whole number of weeks away (7 or 14 days) is possible unless the caller saw a reschedule cue (`RESCHEDULE_CUE`, passed as `rescheduled`), since a weekly series looks the same; further apart it is possible, with `moved` as a hint that the date differs. A similar title (0.3) on the same date is possible; an undated ask reaches possible only. Titles whose numbers differ ("Assignment 1", "Assignment 2"; neither set within the other, so "Quiz 3 due 15" still matches "Quiz 3") never match, and closed targets are never candidates. Ties follow the commitment matcher: `tie: true` and `candidates` (earliest due first), `targetId` the earliest. `findTitleDuplicate` is untouched; its callers keep their behaviour until the plan-aware reconciler moves them. The reference resolver applies a strong moved match as an update and asks, with no chooser, where the date differs on a possible match. The 20x generated suite holds only two cases of each tie kind; raising that is a count change to the whole size, left for its own change.
