# Activity store

Status: implemented (ingest, store, owner routes, the physiology vocabulary, and the message family contract); the importers are in `integrations/activity-importers` and [Importing your data](../operations/importing-your-data.md); live pollers are a later change. Owns: the append-only `activity_events` table, its ingest and read routes, the source registry, the content gate, retention and undo. The capture side is [Desktop activity agent](desktop-activity-agent.md). The published request schema is `platform/contracts/activity-events-schema.v1.json`.

Every non-plan data source (the desktop agent, browser history, plays, messages, sleep, weather, phone shortcuts) lands as rows in one table, so a later predictor reads one place. Nothing in the engine, scheduler or pulse reads these tables: a write queues no recalculation, and `portal/server/watch-history/engine-blind.test.ts` fails if any other source file names them. There are no MCP tools for it (the tool list is capped).

## Tables (migration 0148)

- `activity_events`: `id`, `user_id`, `source`, `kind`, `event_key` (idempotency, unique with user and source), `device`, `ts_start`, `ts_end` (null for an instant), `tz_offset_min` (minutes east of UTC at the event, null when unknown), `approximate`, `attrs` (jsonb, at most 8 KB), `content` (text, at most 64 KB, only when the source's gate is on), `import_id`, `ingested_via` (the posting agent's name), `ingested_at`. A trigger refuses every `UPDATE`. `DELETE` and `TRUNCATE` stay possible: restore and the test harness truncate every backup table. Store code deletes only for undo-import, purge-by-source and the retention purge. A wrong interval is corrected by a new row of kind `correction` whose `attrs.corrects` names the event key; raw rows are never rewritten.
- `activity_imports`: one row per file loaded in bulk (`source`, `filename`, `sha256`, `event_count`), unique per user and `sha256`, so concurrent first batches of one file resolve to a single row.
- `activity_source_state`: per source, `content_enabled` (default false), `retention_days` (null keeps permanently), and a `cursor` for later pollers. An absent row means the defaults: the gate takes `OPENRHEN_ACTIVITY_CONTENT_DEFAULT` (off unless set to `on`), retention is permanent.

Sources and kinds added with the Takeout importers (Timeline, Google Chat, Access Log Activity, Google Photos; formats unverified against a real export, see [Importing your data](../operations/importing-your-data.md)): `timeline` (`place_visit`, `activity_segment`, `point`), `google-chat` (`message`, the Gmail attrs shape with `thread_id` the space id), `google-access-log` (`access`; attrs hold only product and activity type, never an IP address or user-agent) and `google-photos` (`photo`, `video`; sidecar metadata only, the media is never read).

`source` and `kind` are checked in code against the registry (`ACTIVITY_SOURCES` in `platform/contracts/src/activity-events.ts`), not by a database constraint, so a new source needs no migration. Each source has a `schemaVersion`; `correction` is accepted as a kind for every source.

## Derived rows

Source `derived` (schemaVersion 1) holds what a reader extracted from other rows, never the text itself. Kinds: `msg_class` (`class` person, bulk, automated, transaction or calendar, `reasons` from a closed list, `tier`), `fact` (`fact_id`, `fact_type` ask, commitment, event or deadline), `fact_status` (`fact_id`, `status` proposed, confirmed, rescheduled, cancelled, done, superseded or source_gone, `valid_from`), `override` (`fact_id`, `field`, `new_value`) and `label` (his ground-truth `answer`, `null` for "no such value"; required `field`, one of the attrs of the labelled `msg_class` or `fact`, refused with the list otherwise; optional `slice` random or stratified, and `stratum`). Source `derived-shadow` holds the extractor output (`msg_class`, `fact` only, under the same validators; no status, override, label or `correction` for any writer) of an extractor version not yet promoted, so two versions can be compared on the eval set; reads never show it unless `source=derived-shadow` is asked for by name, and `writeShadowRows` (in-process, beside `writeDerivedRows`) is its writer. `validateActivityEvent` applies the per-kind rules in `platform/contracts/src/activity-derived.ts` to every writer: an unknown class, reason, status or type is rejected with the allowed values and the fix; attrs are at most 4 KB (half the general limit); `content` is refused; and `attrs.by` is refused because the server derives the actor from the posting agent (`ingested_via`, null for the person). A `fact` row's optional attrs are validated when present: `span` (`{start, end, hash}`, at most 200 code points, never text), `when` (`ref_time`, `tz`, at most 3 `candidates`, `ambiguous`, optional `raw` offsets; not ambiguous means exactly one candidate), `direction` (`in` or `out`), `who` (exactly the sender for `in`, 1 to 3 recipients as typed for `out`, and it needs `direction`), `conversation_key` (`gmail:<thread id>`), `ics_uid`, `ics_sequence` (the ICS SEQUENCE, a whole number from 0) and `ics_organizer` (one lower-case address), both needing `ics_uid`, `links` (up to 3 of `cancel`, `reschedule`, `repeat` with a `target_fact_id`, never the row's own) and `model` (`id`, optional `digest`). A `t2` or `t3` fact must carry `model` and `span` (a quote that does not ground is not written), and a `t0` fact must not carry `model`. `review_reason` is one of the stored codes `ambiguous_date`, `unmatched_update`, `over_cap`, `low_signal`; `expired`, `update_seen` and `t3_deferred` are computed at read and refused as stored values. A message label's `field` also accepts `fact_types` (a list of fact types, `[]` for none, never `null`) and `sensitive` (true or false). The validators cannot know where `direction` and `who` came from, so the extractor must take them from `messageFactContext` (the collector's `from_self`, never a model). Fact identity for the model extractors is `factIdN2` (sha1 over `n2`, splitter `s1`, conversation key, the normalised sentence the grounded quote starts in, and `ics_uid`; no fact type, no quote), `groundQuote` is the gate (a quote must match the message exactly once and span at most 200 code points, else it is rejected and counted by `tallyGrounding`), and `n1` is frozen and unused by them. The key set of a `fact` row is closed (`source_event_id`, `fact_id`, `fact_type`, `confidence`, `tier`, `extractor`, `extractor_version` and the attrs above), so no free-text field can be added; `tier` is required once a row carries a `span` or `model`, and only `t2` and `t3` name a model. The gate also refuses a span that starts on a `>` quoted line, text over 200,000 code points, and a sentence with no letter or digit, and `n2` strips leading `>` markers from each line before hashing. The `n2` normaliser is NFKC plus JavaScript's `\s` for whitespace, so it is only as stable as that definition. **Known limits of splitter `s1` (frozen on merge; every rule that can merge two sentences or split one):** a stop after `Mr`, `Mrs`, `Ms`, `Dr`, `Prof`, `Sr`, `Jr`, `vs`, `e.g` or `i.e` never ends a sentence; after `etc`, `approx`, `cf`, `fig`, `inc`, `ltd`, `co` or a dotted initialism (`U.S.A.`) it ends one unless a lower-case word or a digit follows, so "paper etc. and" merges and "paper etc. then" does not; "1." at the start of a unit is a list number; a single newline never ends a sentence (mail is hard-wrapped), so two sentences with no stop between them are one unit; a sentence with no punctuation runs to the next blank line, bullet, quote change or the 400 code point cap. A single capital letter always ends a sentence, so "John F. Kennedy" splits into two units (harmless) rather than "Plan B. Please book" merging. Two facts in one merged unit share one fact id, so a status or label on one applies to both. A fact id is a plain sha1 and outlives retention, so for short or stock sentences it is guessable by anyone holding the database or a backup. A message with no header attrs is `unknown` and gets no `msg_class` row. **Model-fact helpers (pure, `integrations/communication-readers`, nothing wired yet).** `hostedEligibility` decides whether a message and each of up to 3 context messages may go to the hosted model (the context checked is exactly what the prompt carries, the newest 3 by one shared selector, and link-candidate quotes are checked the same way; `buildFactPrompt` accepts context only from `vettedContext` or `localContext` and candidates only from `vettedCandidates` or `localCandidates`, and a denied candidate quote holds the message back): all must be `person` class with no failed authentication and a sender address, match no deny-list class (one-time codes in several languages, banking, bills and payment, passwords and reset links, health, legal and other sensitive topics, keys and tokens), and not come from a sender in the versioned list (`DENY_LIST_VERSION`) or one he labelled sensitive; anything missing is a denial, it returns reason codes and never text, a context message that fails is dropped, and one that fails for what it says makes the thread sensitive so the message is held back too. The deny-list is reactive, so the first mail from a new sensitive sender can pass. `buildFactPrompt` fences the message and context as untrusted data (a fresh boundary token, control and hidden characters removed, fence-like runs spaced, quoted `>` lines omitted, length caps) after a fixed instruction block (`PROMPT_VERSION`); it sends the sender address only, never names, To or Cc. The model returns only a `quote` and a `type` per fact (at most 5), plus an optional link to a numbered candidate from `linkCandidates` (at most 5, same conversation, earlier messages); `parseFactReply` is strict and refuses a date, id, who or direction under its own reason. `resolveWhen` reads dates from the grounded quote with `chrono-node` (pinned exact; English, German, French, Spanish, Italian, Dutch, Portuguese, Russian, Swedish, Ukrainian, Japanese and Chinese with a script or region), against the message time and the owner's zone with its own DST rules; a day with no time, "at 3" without am/pm, a skipped or repeated clock time, "3/4", several dates, a recurrence, a day number left unread, a sure reading that starts before the message and any other language are `ambiguous`; a month name then a bare number is the day ("Dec 25"), a bare ordinal ("by the 15th") is the next such day, an overnight range ends the next day and "Friday midnight" offers the start of Saturday first. `integrations/communication-readers` holds the pure functions the readers share: `classifyMessage`, `factId` (sha1 over the frozen `n1` normaliser version), the `event_key` rules, the evidence-span locator (code-point offsets plus a truncated content hash) and status resolution (latest `valid_from`, ties by person over Mark over extractor, `expired` computed at read).

## Drift rows

Source `drift` (schemaVersion 1, class `drift`) holds the drift detector's own rows ([Drift detector](drift.md)). Kinds: `work_label` (whether an area counts as work: `area_id`, `label` `work` or `not_work`, `origin` `inferred` or `corrected`; an inferred row carries `model {id}`, `input_hash` (the sha256 of what the model was shown, never the text; low-entropy for a short area name, so it is owner-only like the rest), `prompt_version`, optional `evidence` of at most 200 characters and `confidence`; a corrected row carries `request_id` and may say `unset`, which takes the owner's answer back) and `flag` (a shadow flag: `rule`, `moment_id`, `bucket`, `arm` `shadow`, `holdout`, `thresholds_version`; no writer yet). The validator is `platform/contracts/src/activity-drift.ts`. It checks what a row shows of itself: closed values, the event key (`work_label|<area>|inferred|<hash>|v<prompt>|<model>` or `work_label|<area>|corrected|<request id>`, so a text, prompt or model change infers again and a retried tap is one row), `arm` is `shadow`, `holdout` follows the moment id, `bucket` the start time. Attrs are at most 4 KB, `content` and an end time are refused, and so is `by`. The generic `correction` kind is not accepted: a correction is a `work_label` row of origin `corrected`.

Who may write and read. No token scope writes the source (`activityEventScope` answers owner-only, with a message for drift, even in a batch with other rows), so a capture token cannot forge a flag or a label. The model's rows are written in-process with `ingested_via = 'drift:label'`; the owner's answers go through `PUT /api/work-labels/[areaId]` and carry `ingested_via` NULL. Readers filter on that stamp (`resolveWorkLabels`), so a row whose origin and writer disagree is ignored rather than trusted. A token reads the source only with `read:activity-drift` as well as `read:activity-event` (the third source class, kept out of `SCOPES_SUPPORTED` like the other two); the owner session reads it. Retention is never applied to it and cannot be set on it, and purging the source deletes the owner's answers with the rest, so do that only meaning to.

## Ingest

`POST /api/activity-events`, scope `write:activity-event` (preset `activity-capture`, which grants nothing else). Send the token in the `X-OpenRhen-Token` header. The scope each row needs follows its source and kind: raw sources and derived `override` and `fact_status` need `write:activity-event`; derived `fact` and `msg_class`, and any `derived-shadow` row, need `write:activity-derived` (an extractor token, which therefore cannot write a status or override and never outranks a person's confirmed status); derived `label`, the generic `correction` kind and any other derived kind are the owner session's alone, and a token is refused with the fix. A batch needs the union of its rows' scopes, and a row or body that could never be stored (not an object, no text `source`) needs only `write:activity-event`, so the handler rejects that row alone. The check reads the body under the same 2 MB cap as the handler and answers an oversize body with the same 413. The runner writes in-process, so scopes bind only Mark and external tokens. `by` is never sent: the server records the posting agent as `ingested_via` (null for the person), and only rows with `ingested_via IS NULL` count as his labels. Create the token from the agent-tokens card in the portal, or with `rhen agent-token create --name <agent> --scopes activity-capture`.

A batch is `{"schema": 1, "device": "...", "events": [{"id", "source", "kind", "start", "end"?, "attrs"?, "content"?, "tzOffsetMin"?, "approximate"?}]}`, up to 1000 events and 2 MB. Times are RFC 3339, second or millisecond precision. An offset (`+11:00`) is accepted, normalised to UTC, and recorded as `tz_offset_min`; a `Z` time leaves it unknown, and an explicit `tzOffsetMin` wins. `+00:00` is an offset like any other and gives 0 (an importer whose source cannot tell local time, such as Discord, sends `Z` or leaves it out). An offset must lie within -14:00 to +14:00, the date must exist, the year must be 1970 to 2200, and `id`, `device`, `content` and `attrs` may not hold a NUL or a lone surrogate (Postgres refuses them): such an event is rejected alone, with a plain reason, never as a server error.

**Single-event shorthand.** A body with no `schema` and no `events` but a `source` is one event: `{"source", "kind", "start", "id"?, "device"?, "end"?, "attrs"?, "content"?}`. When `id` is given it is the event key; otherwise the server derives it from a hash of source, kind, start (to the second), device and attrs, so a shortcut that fires twice for the same second stores once.

**Heartbeat and coverage rows.** Two kinds belong to no source's `kinds` list; the ingest judges them with the whole batch in view, the way `validateActivityBatch` does for an adapter's tests. A `heartbeat` (`attrs {status: "ok" | "error", error?}`, key `hb:<batch device>:<UTC hour>:<status>`) says a collector is alive; a `coverage` row (`start`, `end` at most 31 days, `attrs {complete: true, scope?, rev?}`, key `cov:<scope>:<start>:<end>[:r<rev>]`) says every message of that window was accepted. Both take no `content`. A source takes them when its registry entry declares `availability` (a heartbeat needs delivery `live` or `periodic`; coverage needs a `complete` feed, or an `availability` with no feeds), or when its family is `message@1`; the mail source declares `availability` (periodic, origin `account`, no feeds), so its collector can adopt them first. Any other source gets a rejection naming a kind it does post. A wrong key is rejected with the exact key to send (the heartbeat key names the batch `device`, so send `device` at the top of the batch; a shorthand post without an `id` gets the server's `h:` key and is rejected the same way). A batch with an `import` is not live and may carry coverage windows older than 400 days. The post-pass refuses a coverage row when any other event of the same source in the batch was rejected (or a rejected event's source could not be read), with the index to fix: resend the batch, or send coverage in a later batch once every row is accepted. A coverage row must name `attrs.scope` (the account, mailbox or channel it covers) when its source is in the message family or declares `availability` with no feeds (the mail source), so a window of one account cannot hide silence on another; a scope-less or blank row (or one with leading or trailing spaces) is rejected, and the text gives the id to send. Coverage is append-only per window and judged per batch, never replaced, so a reader must take the union of every claimed window per (source, scope), not the newest row. A source refused a kind is told which kind it does post, and the owner must declare `availability` on its registry entry to enable the rest. The health reader (`portal/server/data-flow/health-reader.ts`) reads them: heartbeat and coverage rows are excluded from arrivals, kinds seen and learned rhythm, and a source that has posted either is judged by its covered-up-to point (the latest `end` per scope, the oldest of its live scopes overall) instead of its newest arrival. `thresholdFor` puts the owner's setting (not yet present) and the collector's declared cadence first, and a coverage source with no number is late at 12 h and stale at 24 h. The doctor's `source_late` item words these as "read up to" and is blocking at stale for a source that `changesPlan`; `DoctorReport.planInputs` carries the one-sentence statement of what the plan is built from, and `DoctorReport.processing` the messages collected against the end states recorded in `reconcile:<source>` runs. See docs/operations/posting-messages.md section 5.

The response is `{message, schema, added, alreadyHeld, contentDropped, rejected: [{index, reason}], held, importId, ingestedVia}`. `held` is empty except for source `physiology` (below). `message` is one plain-English line, because a phone shortcut shows the body as it is.

- A bad event rejects itself, not the batch; its reason names the exact fix (the known sources or kinds, the limit, the field). A rejected shorthand event answers 400 with that reason as `error`.
- A key already held (in the store, or earlier in the same batch) is `alreadyHeld`: never an error, never a change.
- Content is dropped, and counted in `contentDropped`, when the source's gate is off, except in a file import (a batch that carries `import` or `importId`): importing your own file is the consent, so its text is kept whatever the gate says. The gate governs continuous collectors (rhen-watch, phone shortcuts, pollers); a collector must not send `import` to get around a gate that is off. A source with no saved setting takes the server default, `OPENRHEN_ACTIVITY_CONTENT_DEFAULT` (`on` or `off`, default `off`); a saved setting wins both ways.
- While the pulse is lapsed a token is held with a 428 on every route except `POST /api/activity-events` and `GET /api/activity-imports`: a passive recorder (rhen-watch, a phone shortcut with no retry) posts exactly while the owner is away, and the post stores events but returns none. Reading events back stays held.
- Whole-request errors: malformed JSON, a wrong `schema`, an empty or oversized list (400), a body over 2 MB (413), a failed token.

**Imports.** The first batch of a file carries `"import": {"sha256", "filename"}`; the response returns `importId`, and later batches carry `"importId"`. `GET /api/activity-imports?sha256=<hex>` answers `{held, importId?, eventCount?}` so an importer can skip a file already held; it takes the capture scope `write:activity-event`. With no `sha256` it lists recent imports (file names and counts). **An import is one source:** every event in its batches must have the import's source (`import.source`, else the first valid event's), and any other is rejected, so undoing an import or purging a source can never reach another source's events. If every event in a first batch is rejected, send `import.source` explicitly.

## Physiology and health-class sources

Source `physiology` (schemaVersion 1) is the generic vocabulary for anything a wearable, phone or health app measures. Core defines the shape and the endpoint; the user's own collector maps its data onto the kinds and posts to `POST /api/activity-events`. Core holds no poller, adapter, provider key or vendor name. Kinds: `heart_rate`, `heart_rate_dense`, `hrv`, `stress`, `score_series`, `respiration`, `spo2`, `skin_temp`, `steps`, `movement`, `sleep`, `daily`, `score`, `workout`, plus the generic `correction`. The collector's guide is [Posting physiology data](../operations/posting-physiology-data.md); the published shape is `platform/contracts/physiology-schema.v1.json`. Physiology rows are context for a predictor and never change what the plan allows; the engine never imports the module (`engine-blind.test.ts`).

Every physiology row is a period row identified by one canonical key, `<kind>|<attrs.device>|<period>|v<attrs.v>`, where the period is the UTC hour or 5-minute slot start (RFC 3339 with milliseconds and `Z`), the `local_date` for `sleep` and `daily`, `<score_name>@<period start>` for `score`, and `x:<ext_id>` (else the start to the second) for `workout`; a `correction` is `correction|<target key>|<n>`. `attrs.route` (how the row was obtained) is never in the key, so one fact from two routes or collectors has one identity. `validateActivityEvent` applies the per-kind rules in `platform/contracts/src/activity-physiology.ts` to every writer, the way it applies the derived rules: closed attr lists, closed value lists, label character sets and lengths, the sample and segment rules (`step_s` divides the period, `min` and `max` are the true extremes and `avg` the mean within 0.05 or half a unit of its own precision, readings inside a plausible range per unit or inside their scale), units, no `content`, and the key. A rejection names the field and the fix, and a wrong key names the key it expected. A shorthand post that carries no `id` gets the server-made `h:<hash>` key, which is not canonical, so it is rejected with the id to send. The batch-level `device` column is informational for physiology and is not checked against `attrs.device`.

The store is first-write-wins, so a fuller re-post of a period needs the next `v`. Each physiology event answered `alreadyHeld` comes back in the response's `held` list as `{index, key, v, coverage_s, n}` taken from the held row (one lookup per held key on the unique key index, physiology only), so a collector that lost its state sees what is stored, compares, and re-posts with `v` one higher. This is metadata only (the version, coverage and count of a row you posted the key of): a write-only `activity-capture` token learns those three numbers for keys it posts, and never any value, content or row.

## Message family

`message@1` is the neutral family for messages from any mailbox, chat or notification feed, posted by the user's own collector. Core defines the shape and the endpoint and holds no poller, adapter or vendor name. An extension registers a source with `family: "message@1"` and the one kind `message`; `validateActivityEvent` then applies `platform/contracts/src/activity-message.ts` to its events, the way it applies the physiology rules. The collector's guide is [Posting messages](../operations/posting-messages.md). Event keys are unique per `(user_id, source, event_key)` (`activity_events_key_idx`, migration 0148, and the insert's `ON CONFLICT`), so a `mid:<id>` from one source cannot collide with the same id from another. The `attrs.fp` fingerprint has no time in it by design: any later comparison across rows must also require sent times within 60 seconds (`MESSAGE_FINGERPRINT_TIME_TOLERANCE_SECONDS`); that lookup is slice B2 and does not exist yet, so nothing merges on `fp` alone. The no-id `fp:` key can drop two distinct same-minute messages with identical text and does not catch most pasted copies (see the guide).

`start` is the sent time and `content` the text (gated like any content). `attrs` is a closed list: `message_id`, `from` (required), `to`, `from_self`, `direction`, `channel`, `thread_id`, `subject`. The key is canonical, and a wrong `id` is rejected naming the expected one: `mid:<normalised message_id>` when the event has an id (its sha256 first 40 hex when that would pass 200 characters), else `fp:<40 hex>` over sender, sent time to the minute and text. A message with neither an id nor text is rejected. The server also stores `attrs.fp`, 32 hex of sha256 over the normalised sender and normalised text (NFKC, lower-case, zero-width characters and whitespace removed, first 8192 code points), computed in the validator from the raw `content` and so present even when the content gate drops the text; a sent `fp` is rejected. The pure helper is `messageFingerprint`, with frozen vectors in `platform/contracts/message-fingerprint-vectors.v1.json`.

Today this is a contract only. The store does not yet compare fingerprints across sources: a pasted copy of a collected message is held twice until the cross-source check is wired into ingest, and `alreadyHeld` still means the same key. The store, the ingest response and the health reader are unchanged by the family. The grandfathered mail source is not in the family and its rows are unchanged (no `attrs.fp`, its own id key); it can adopt the family later by registering under it, since the shared field names, including `message_id`, already match. Messages are information only: nothing here changes what the plan allows, and the engine never imports the module (`engine-blind.test.ts`).

**Source class.** A registry entry may carry `class`. `physiology`, `apple-health` and `iphone-health` are class `health` (the two legacy sources gain only the class; they are not renamed). A database token reads health-class rows only with `read:activity-health` as well as `read:activity-event` (class `drift`, source `drift`, likewise needs `read:activity-drift`). The scope is known to the token vocabulary (`rhen agent-token create --scopes read:activity-event,read:activity-health`) but is deliberately not in `SCOPES_SUPPORTED`, so a default OAuth grant never includes it and a client that asks for it gets `invalid_scope`. Without it `GET /api/activity-events` leaves the health sources out and returns `withheld` (their names) and `withheldNote` (the missing scope) beside `events` and `next`. The owner session, environment tokens and background writers hold no token scopes and read everything. This withholds `apple-health` and `iphone-health` rows from tokens and connectors that held only `read:activity-event` before ([Versions](../protocol/versions.md)). Legacy rows are read alongside `physiology`: `apple-health` sleep intervals are `sleep` segments, `apple-health` workout and steps correspond to the `physiology` kinds of the same names, and `iphone-health` `*_day` rows are `daily` fields.

**Classes and scopes.** There are two classes, `health` and `whereabouts`, and one table maps each to its read scope (`ACTIVITY_CLASS_READ_SCOPE`): `health` needs `read:activity-health`, `whereabouts` needs `read:activity-whereabouts`. A database token reads a classed source only with its class's scope as well as `read:activity-event`; the owner session, environment tokens and background writers read everything. `write:place-model` is the scope for writing the owner's place model. All three scopes are known to the token vocabulary and none is in `SCOPES_SUPPORTED`, so a default OAuth grant never includes them. When sources are left out, the read returns `withheld` (names), `withheldClasses` (a count per class) and `withheldNote` (the missing scopes) beside `events` and `next`. No registry entry is `whereabouts` yet: the sources of that class arrive with the places build.

**Declared inputs.** A registry entry may declare, as data, the positions it supplies (`positionInputs`), the attrs that hold a stable place id from an export (`extIdAttrs`) and what a place hint may copy from its rows (`placeHints`). A reader takes every source that declares them and holds no source names. The import sources that carry positions declare them (one of them also declares an external place id attr), one declares positions that only join existing places, and one declares a name and list attr for hints. Core declares no imported-type attr or value set: a provider's vocabulary belongs to the overlay.

## Run rows for silent paths

Paths that used to leave no trace write a row to `integration_sync_runs` (the table the connections and the doctor read), through `recordRun` in `portal/server/persistence/postgres/run-log.ts`. The table's constraints allow only the triggers `manual` and `scheduled` and the statuses `synced`, `needs_review`, `failed` and `not_configured`, so these rows use those. The provider holds a namespace and a name, and the doctor's sync check skips any provider with a colon, so these are not syncs. Rows are pruned after 90 days per provider, and writing one never fails the work it describes.

| Provider | Written by | Trigger and status |
| --- | --- | --- |
| `import:<source>` | `POST /api/activity-imports/runs`, called by `rhen import` once per job | `manual`; `synced`, `needs_review` (rows skipped, rejected or warned), `failed` |
| `ingest:<source>` or `ingest:unknown` | `POST /api/activity-events`, when events were rejected, also if the batch then rolled back | `scheduled`; `needs_review`, summary `{rejected, firstReason}`; at most one row per source per hour |
| `job:travel-lookup`, `job:plan-map-sweep` | the travel tick and the plan-map sweep, when one did work or failed (a quiet tick writes nothing) | the request's trigger; `synced` or `failed` |
| `device:handheld` | `GET /api/device/now` (an accepted poll, `synced`) and a refused device-route call (`failed`, with the reason) | `scheduled`; one row per hour per status |

`POST /api/activity-imports/runs` takes the capture scope `write:activity-event` and a body `{source, status, startedAt, finishedAt, summary: {file, events, skipped, rejected, truncated, warnings, error?}}`: `source` is an activity source or `youtube-watch-history`, `status` is one of the first three above, `file` is a base name, `warnings` holds at most 20 items. An unknown source answers 400 with the valid ones. Nothing shows these rows yet beyond the table itself.

**The per-device view.** The summary's `devices` lists, for the health-class sources only, one entry per source, device, kind and collector: `{source, device, kind, ingestedVia, lastEventAt, lastIngestedAt, rows30d}`. The device is `attrs.device` for `physiology`, else `attrs.source_name`, else the batch's `device` column (the legacy sources); the collector is the token name that posted (`ingested_via`, null for the owner), so a live collector cannot hide a dead daily one. It is computed from the stored rows by one bounded range scan of the last 30 days over `activity_events_user_source_time_idx` (user, source, `ts_start`) and then grouped, with nothing stored for it; an integration test times it at 100k rows. It can say only "no data newer than X": it cannot tell a device that is not worn from one that has not synced. Where a collector sees its own health: the response of each post (`rejected` with the reason for each, `held` for what is stored), and this view for the owner.

**Deliberately not built (deferred until a reader needs freshness).** No reject counters (they need a rolling window, attribution of unknown sources and recovery rules, and a state row inserted without `content_enabled = activityContentDefault()` would flip that source's content gate); no staleness judgement or doctor items (judging "stale" needs an expected cadence, and a cadence setting is an opt-in, a quiet off switch; the right source is observed history). The reader rule for choosing between rows of one device, kind and period is in the collector guide, with no function until a reader exists.

## Reading back

`GET /api/activity-events?source=&kind=&from=&to=&as_of=&limit=&after=` returns `{events, next}` in time order (start, then id), `to` exclusive, up to 1000 per page. Pass `next` as `after` for the following page. Rows of source `derived` that an extractor wrote (`msg_class`, `fact`, carrying `attrs.extractor` and `attrs.extractor_version`) are shown for the extractor's active version only; with no active version, or a row naming none, they are not shown. A person's rows (`fact_status`, `override`, `label`) belong to no version and always are. `as_of` (RFC 3339 with offset) reads as the store stood then: rows with `ingested_at <= as_of`, and the version that was active at that time (the latest promotion at or before it, from `extractor_state.cursor.promotions`), so an old `as_of` returns the same rows however many runs or promotions follow. A promotion entry with an unreadable time is ignored, and a state row with no promotion record has no version at any `as_of` (so shows no extractor rows). The owner session may always read; a token needs `read:activity-event`, and `read:activity-health` as well to see sources of class `health` (above). **That scope exposes `content` (message text, titles, search text) over a token**, so grant it only to an agent you would trust with that text. The `activity-capture` preset does not include it.

## Owner routes

Owner session only, never a token: `GET /api/activity-events/summary` (counts, last event and settings per source, `devices` (below), recent imports, and `extractors` with `derivedBehind`, below; `lastPurge` is null while a source has no retention; `?report=eval` adds the eval report, below), `PUT /api/activity-sources/:source` (`{contentEnabled?, retentionDays?}`), `DELETE /api/activity-imports/:id` (undo an import: its events and its record), `DELETE /api/activity-sources/:source/events` (purge a source, including its import records; not undoable).

The content gate decides whether a continuous collector's text is stored from then on (a file import always keeps its text); turning it off deletes nothing already stored (use the purge for that). It is a consent gate, not a feature switch.

## Retention

**Retention is permanent by default and runs when you set it.** `PUT /api/activity-sources/:source {retentionDays}` saves the setting; a source with no setting (or no `activity_source_state` row) is never touched. The derived tick (`runDerivedTick`, on the worker loop) runs the retention pass after the extractors, under the same per-person advisory lock as the runner and the delete paths. For each source with `retention_days` set it deletes rows whose `COALESCE(ts_end, ts_start)` (and `ts_start`, so the index bounds the scan) is older than the cutoff, in batches of 5000, at most 4 batches per tick (`RETENTION_BATCHES_PER_TICK`); the tick answers `more` and the worker comes back soon. A failed pass rolls back alone (a savepoint) and is reported in the tick's `retention.error`. The summary shows `retentionPurge` (`not_set` or `scheduled`) and `lastPurge` (rows deleted and when, for the last pass that deleted something; kept in `activity_source_state.cursor`). `purgeExpiredActivity` (`activity-store.ts`) runs the same code outside the tick.

What retention keeps: rows of source `derived`, `derived-shadow` and `drift` are never retention-deleted, even if those sources are given a setting, so `msg_class` history stays for the predictor. Keeping derived facts after their source is retention-deleted is intended (the owner wants the most data kept): retention does not use the lineage delete helper, so a derived row survives when its source expires (its lineage rows cascade away and it reads back as an orphan). Before a batch goes, the runner appends a `fact_status` row `source_gone` (author `extractor:retention`, `valid_from` now) for every derived `fact` whose resolved status is open and whose lineage sources are all in that batch, in the same transaction; a fact with a source left outside the batch is marked when the last one goes, and a closed fact is skipped, so reruns write nothing. `source_gone` is the only status the runner can write (`appendRunnerFactStatusTx` refuses any other, and it has no path to an override or label). Retention cannot be set on `derived` or `derived-shadow` (the settings route refuses it, saying to set it on the raw source), and `retentionDays` is 1 to 36500; a stored value that gives no valid date skips that source for the pass, reported in the pass result and `lastPurge.skipped`, while the person's other sources still run. Import records are left, so a retention-purged file still counts as held. Explicit deletes (undo import, purge a source) still delete the derived rows via lineage.

## Derived rows, lineage and extractor state

Rows with `source = 'derived'` (and later `derived-shadow`) are projections of other rows. `derived_lineage (user_id, derived_id, source_id)` records which source rows each was read from (both ids cascade from `activity_events`; index on `source_id`); `recordLineage` in `derived-lineage-store.ts` is idempotent and links only the person's own rows. Every source-delete path (`deleteActivityImport`, `purgeActivitySource`, one transaction per batch of 5000) first calls `deleteDerivedForSources`, which deletes the derived rows whose lineage touches the batch **only when no lineage source is left outside it**, so a fact read from two messages goes with the last one. It must run before the source rows go, because the cascade removes the lineage rows with them. Deleting the user cascades through both foreign keys. Retention does not call it (see Retention). Each batch first takes the per-person advisory lock the runner also takes (`activity-lock.ts`), so a delete and a derived write for the same person never interleave and leave no orphans.

`extractor_state (user_id, extractor, version)` holds a cursor, `last_ok_at`, `last_error` and `active`; a partial unique index allows one active version per extractor. `active` records which version is promoted; it is not a setting. Index `(user_id, source, ingested_at)` serves the runner's scan and `as_of` reads.

Migration 0151 adds two partial indexes on `activity_events`, partial so raw mail rows (millions) are never indexed: `(user_id, (attrs->>'fact_id')) WHERE kind = 'fact'` finds a fact across reruns, and `(user_id, source, kind) WHERE source IN ('derived', 'derived-shadow')` serves derived reads. A plain `CREATE INDEX` inside a drizzle migration blocks writes to `activity_events` (ingest, the worker tick) until it finishes; the build time is stated in the PR that carries the migration. It also adds `derived_settings` (one row per person; an absent row reads as the defaults): `ollama_url` (an http(s) URL with no credentials, only the address and port), `t2_model`, `t3_model`, `t3_daily_message_cap` (default 50), `t3_daily_token_cap` (200000), `backfill_days` (90), each bounded by a CHECK that matches `parseDerivedSettingsPatch`. `GET` and `PUT /api/derived-settings` read and merge it (a field left out keeps its value, text sent as null clears it, a bad value is a 400 naming the range and the fix); both are owner-only (`OWNER_READS`, `OWNER_ROUTES`) because the URL is a network address and the settings decide where mail text goes, and no MCP tool exposes them. The route only stores the address (as its parsed origin; control characters, backslashes and anything but a plain `scheme://host[:port]` are refused); it does not decide where the portal may call. The deny-list (loopback, link-local, the metadata address, compose-service names, the proxy's own subnets) belongs to the outbound proxy and is enforced at call time (slice 2b-3a). The hosted API key is not in this table: it is a saved key (`app_secrets`), and a restore empties saved keys. `derived_model_calls (id, user_id, source_event_key, at, tier, model, tokens_in, tokens_out, reason)` is the audit of every model send: the event key, never content or a key. A trigger refuses UPDATE (DELETE stays possible for the user cascade), as for `activity_events`. The call policy (`portal/server/derived/call-policy.ts`) is the one function every model call goes through and the only writer: one row per hosted (`t3`) send, including each timeout retry and repair retry, written after the attempt with the provider's token counts (an estimate of four characters a token when it gave none, and 0 out on a failure); local (`t2`) calls write none. The daily caps count these rows over the last 24 hours (`GET /api/derived-settings` returns the count as `usage`). The policy warms a local model before its first call, retries a timeout twice (5 s, then 20 s), repairs bad output once, runs local calls one at a time, checks hosted eligibility at the call through an injected checker immediately before sending, checks the message and token caps before every attempt, and refuses the model makers the hosted provider's descriptor lists (its retention rule). The policy and the proxy-call helper name no provider: each tier's provider is a `ModelProviderDescriptor` (`platform/contracts/src/connections/model-providers.ts`: connection id, label, secret name, body fields, refused makers, wording), injected as `PolicyDeps.hosted` and `ModelTransportDeps.providers`; a provider's own name lives in its descriptor and its connection under `integrations/outbound-proxy/src/connections/<provider>/`. `POST /api/derived-settings/test` (owner-only) runs the settings card's Test button with fixed synthetic text; it skips the mail-eligibility rule because no mail is sent, but obeys the caps and writes its row (event key `test:synthetic`). The hosted key is the sealed secret `hosted_model_api_key` (the name the descriptor gives), read only by `portal/integrations/models/model-proxy-client.ts` (an allow-listed reader) and sent in the proxy call's body.

## Backups

All the activity tables, including `derived_lineage`, `extractor_state`, `derived_settings` and `derived_model_calls` (below), are in the backup (format 26 added the last two, last of the core tables; format 25 the two comparison tables; format 24 the first two; format 23 streamed the events, 22 first held the activity tables, 21 the offer log; older backups restore the newer tables empty, lineage restored after the events it points at). The JSON backup is one document with one checksum, built in memory, and that cannot hold the events at scale: measured with synthetic rows (a desktop-agent row with a small `attrs`), 1 million rows made a 453 MB file and about 2.4 GB of process memory, and 2 million failed with `RangeError: Invalid string length` (V8's string limit).

So `activity_events` is a **streamed section**: its rows are written to `<backup name>.activity-events.ndjson` beside the JSON, one row per line in `id` order, straight from a Postgres cursor inside the same repeatable-read snapshot as the rest of the backup (`backup-format.ts` `readAllTables`, `streamed-sections.ts`). The JSON holds the import records and per-source settings as before, an empty `tables.activity_events`, and a `streamed.activity_events` entry with the file name, row count, byte size and SHA-256. `db:restore:verify` checks the section before touching a database, then inserts it in batches after `users` and `activity_imports`, and reads the restored table back to compare its row count and SHA-256. Measured at 300,000 and 2,000,000 rows, writing and restoring each stays within a fixed memory bound that does not grow with the row count (`activity-backup-scale.integration.test.ts`). The pg_dump taken before a migration holds the events as well.

## The derived-rows runner

`POST /api/integrations/derived/tick` (`{trigger: "scheduled" | "manual"}`, worker-token or owner auth like the travel tick) runs the extractors in `portal/server/derived`; the worker loop only POSTs it (every minute, at once while a run filled its batches). There is no off setting. One T0 tick (the model extractors have their own tick, below) is one transaction under the per-person advisory lock: a second run, `manual` included, answers `busy`. The T0 extractors are `msg-class-t0` and `fact-ics` (below), each with its own cursor and state; an extractor may set `oldestFirst` (its batch is read oldest message first, so an update sees the invite scanned in the same newest-first backfill batch) and gets `lookups` (the owner's zone and the stored `fact` rows of a fact id, including rows made earlier in the same batch, through the partial index on `fact_id`); it still writes nothing itself, and `classifies: false` keeps it out of the eval report's T0 share. `msg-class-t0` version `1` classifies `source=gmail kind=message` rows with `classifyMessage` and writes `msg_class` rows through `writeDerivedRows` (same validators as the API, `ingested_via = extractor:msg-class-t0`, lineage in the same transaction, existing ids returned on conflict). `unknown` writes no row, so progress is two watermarks over `(ingested_at, id)` in `extractor_state.cursor`, both starting one settle margin (60 s) before the first run: forward (live mail, oldest first, held back 60 s so a slow ingest cannot commit behind it) always runs before backfill (history, newest first); batches are 500. A failing message (throw, unreadable attrs, a row the validators refuse) is retried on later ticks up to 3 attempts in all (at most 100 tracked; past that cap a failing message is skipped on its first failure), then skipped: counted in `cursor.skipped`, its id, event key, reason code (`extractor_error`, `row_refused`, `retry_list_full`) and time kept in `cursor.skippedIds` (the last 50), and `last_error` set for that run only (the next clean run clears it, so the ids, not `last_error`, are the lasting trace); it never writes a `fact_status`, `override` or `label`. A derived row is dated no later than the run's `now` (a message with a future `Date` header is clamped, since the store refuses start times over 24 h ahead). A database error (as opposed to a per-message failure) rolls the whole tick back, so the cursor never passes unwritten rows; a row that reliably caused one would block the extractor until fixed, which is why later extractors that copy text into attrs should write per row inside a savepoint. The first version of an extractor is active on creation; `promoteExtractorVersion` flips it atomically and records the time. The summary's `derivedBehind` and per-extractor `behind` are exact counts (two index-range `count(*)` per extractor version, about 130 to 160 ms at 2 million mail rows, so not for polling) of mail past the forward watermark plus the backfill remainder, with `lastOkAt`, `lastError` and `skipped`.

## The model tick

`POST /api/integrations/derived/model-tick` (same auth and body as the T0 tick; the worker loop `derived-model-tick` posts it with a 20 minute timeout, and paces itself by the answer like the T0 loop) drives the extractors that call a language model (`portal/server/derived/model-runner.ts`, registry `model-extractor-registry.ts`). It is separate because a model call takes minutes and the T0 tick is one transaction the worker aborts at 120 s. **No model extractor is registered yet** (`fact-llm` is slice 2b-6); with none the route answers `no_extractors` and does nothing, and a registered one runs without any switch once the mail-understanding settings exist. A model extractor is injected: it gets a message, up to 3 earlier messages of its thread and a `call()` that goes through the one call policy with the model its version is pinned to; it returns rows or a failure and never writes.

Three phases per extractor. **(a)** Under the activity lock, in a short transaction: skip while the circuit is open or another run's lease is valid, take a lease (a random token plus expiry 15 minutes ahead, written into `cursor.lease` and renewed before every message, so it outlives the longest single message and never expires under a live run), and read a batch of at most 20 messages with their text (a version that can use the hosted tier is handed only the thread context the hosted-eligibility rule accepts, asked per context message before the extractor sees it): first those that failed before, then live mail, then history; the history scan only returns messages dated within `backfill_days` of now, and live mail is held back by the 60 s settle margin like the T0 tick. **(b)** With no transaction and no lock, call the model one message at a time under a 5 minute wall-clock budget (half the lease); a tiny first call warms the local model and reads the local model's digest. **(c)** Under the lock again: compare the lease token with the cursor's and the version's `active` flag with the mode the batch was read in (if the token changed, or the version was promoted or demoted meanwhile, everything the run produced is discarded); re-read which of the batch's messages still exist with the same text (a message deleted, or deleted and ingested again, while the model worked has its output dropped); write each row in its own savepoint with `writeDerivedRowsTx` (or `writeShadowRowsTx`), advance the forward and backfill marks past what was done, and release the lease. The release writes `lease: null`, and the reader treats a JSON null, an absent key and a malformed one as no lease.

What a failure costs. A host-level failure (the opening call failing or timing out, a hosted key or rate-limit refusal, three timeouts in a row, or unreachable before the opening call worked) is an outage: the run stops at that message, which keeps its place, nothing is counted against it, and `cursor.circuit` pauses all calls for 1, 2, 5, then 15 minutes (15 after that) for each consecutive failed run; a run that completes clears it. An unreachable answer on one message after the opening call worked (`model_unreachable`), a timeout, bad output the policy's repair retry could not fix, or a throw uses the message's budget of 6 within 24 hours (`cursor.retries[id] = {n, since, code, notBefore}`; the window restarts after 24 hours; a failed message waits 1, 5, 15, 30, then 60 minutes before its next try); past it the message is skipped with `model_timeout`, `model_unreachable`, `bad_output`, `extractor_error` or `row_refused` and stays in `cursor.skippedIds` (the newest 50 ordinary skips, plus, in a shadow run, the skips of labelled messages (up to 5,000, so a poison labelled message is never read again), plus up to 1,000 permanent no-text ones kept apart in the same array so the eval report, which reads that array, never counts them as read) with `cursor.skipped` counting. No mail text is stored or returned: `last_error`, retry codes and result messages have any 8-character run shared with the message or its context replaced by a marker (a validator verdict that quotes the mail is cut down). A message with no stored text (`content` null) is skipped by name with code `no_content`; when the source's content gate is off and nothing in the batch has text, the run answers `no_content` with the exact fix `PUT /api/activity-sources/gmail {"contentEnabled": true}` and consumes nothing.

Pinned models. The first run of a version writes the local and hosted model ids from the settings into `cursor.models` (`{t2: {id, digest}, t3: {id}}`); the version uses those whatever the settings say later (saved settings are for the next version). The digest is read once per run, by the opening call; the first run that reads it records it, and every model-tier `fact` row carries `attrs.model = {id, digest?}` set by the runner with the digest read in that run only, never the pinned value unverified. A later run whose digest differs, or whose digest cannot be confirmed (the host reports none, or the opening call's reply is unusable), answers `model_changed`, reads nothing and opens the same `cursor.circuit` (1, 2, 5, then 15 minutes, with `reason: "model_changed"`), so the host is not probed every tick; a run that confirms the pinned digest clears it. A shadow run honours the retry cool-down for labelled messages like any other. Not yet built: creating the next version when a model setting changes, and the settings route naming it (2b-6, with the extractor). A version is created only when the extractor's `notConfigured(settings)` is null; until then the answer is `not_configured` with the exact PUT.

Shadow runs. A version that is not the active one reads the person's labelled messages (his own `label` rows, `ingested_via IS NULL`) that are not yet in its done list, then live mail from its own forward mark; it never backfills, never selects a labelled message with no text, and never reads a message its labelled lane already read when the forward scan reaches it. Its rows go to source `derived-shadow`. `cursor.shadow = {done, evalCount}`: `done` is a flat array of message event keys, oldest first, which is exactly what the eval report's reader takes (`reachedMessages` in `eval-report-store.ts`): the first `evalCount` are labelled messages (never trimmed below 5,000), the rest live mail (only the newest 2,000 kept), so the list is at most 7,000 keys. A message that is retrying or skipped is never in `done`, and stays in `cursor.retries` or `cursor.skippedIds`, which the reader also checks.

The hosted tier. The runner passes the call policy an eligibility checker; the default refuses everything (`DENY_HOSTED`), so nothing is sent to the hosted model until slice 2b-6 injects the real rule (PR 140's). The answer carries, per extractor, `status` (`ok`, `not_configured`, `no_content`, `circuit_open`, `leased`, `model_changed`, `outage`, `lease_lost`, `busy`), counts, `behind` (exact count of live messages after the forward mark plus history inside the horizon, or for a shadow run the labelled messages still to read plus live mail), `more`, and a `message` that says what happened and names the next call. Known limits: the phase (b) budget stops starting messages after 5 minutes but cannot interrupt a call already running (the lease token, not the clock, protects correctness); context messages are read but only the message itself is lineage-linked, so deleting a context message does not discard a fact read from the next one; `behind` runs its counts after the run's transactions commit (so the lock is not held for them) under a 5 second statement timeout and is null when they do not finish. A circuit that expired with nothing to read is cleared.

## The calendar extractor (`fact-ics`)

`fact-ics` v1 (`portal/server/derived/fact-ics.ts`, rules in `integrations/communication-readers/src/ics-event.ts`) is a T0 extractor, no model: it turns the calendar data the mail source reads out of a message into `event` facts (tier `t0`, `ingested_via = extractor:fact-ics`). It is ACTIVE from its first run, with no switch, and reads incoming mail only (`from_self` mail carries no auth). The mail source writes `attrs.ics` (`uid`, `sequence`, `method`, `organizer`, `recurrence_id`, and `dtstart`, `dtend`, `tzid`, `status`, `summary`) and `attrs.jsonld[]` (`startDate`, `endDate`); `platform/contracts/src/message-calendar-attrs.ts` names them and checks the shape of the event-time ones (`dtstart` and `dtend` are `YYYY-MM-DD`, `...Z` or zone-less ISO, and `dtend` is present only when its zone and form match `dtstart`).

**Malformed calendar attrs.** A mail message whose calendar attrs are malformed is never rejected for it (that would lose the mail). `validateActivityEvent` drops the offending key (`ics.dtstart` with its `dtend`, `ics.dtend`, `ics.tzid`, `ics.status`, `ics.summary`, one JSON-LD `startDate`/`endDate`, a non-list `jsonld`, `auth.dmarc_domain`), stores the rest, and records the dropped names in `attrs.calendar_dropped` (for example `["ics.tzid"]`). A dropped key only ever means less is believed: no `dmarc_domain` leaves the sender untrusted, no `tzid` leaves a floating time. The posting response has no field for this note, so read `calendar_dropped` on the stored row with `GET /api/activity-events?source=gmail&kind=message`; a row already stored is not replaced by posting the same event key again, so the fix belongs in the source that wrote the attr.

**Trust.** Nothing is read unless `attrs.auth` is present, its `dmarc` is `pass`, and `auth.dmarc_domain` (the lower-case `header.from` of that same DMARC result, which the mail source writes when it can read it) equals the domain of the From address. Absent auth is not trusted, and neither is a missing or different `dmarc_domain`: the domain is never guessed, so mail ingested before the mail source wrote it is skipped (`untrusted_no_domain`, `untrusted_domain_mismatch`). SPF and DKIM both passing is not enough, because they carry no alignment and an unaligned pass only proves the forger owns their own domain. The sender is the one mailbox of the From header, read outside quoted strings (`fromAddress`): a header with more than one mailbox, text after the address, an unclosed quote, or an `@`, `<` or `>` in the display part (quoted or not) has no sender and is untrusted, so `"<boss@corp.test>" <bob@evil.test>` is never boss. A cancel or update therefore applies only when DMARC passes for the From domain, that authenticated From is the stored organizer, the uid matches and the SEQUENCE is greater. A reply, counter or refresh (`METHOD:REPLY` and the like) is an invitee's answer, not an event, and is skipped. A message with no `uid`, or an invite with no usable start, writes nothing and is left to the model extractor; so is one whose SEQUENCE is not a whole number from 0 to 2147483647 (`bad_sequence`).

**Identity.** `fact_id` is `factIdN2` over the `ics_uid` slot, a fixed `ics:event` scope in the conversation slot (an event is identified by its uid, not a thread) and the authenticated From address (with `recurrence_id` when there is one). That sender is also the organizer key stored as `ics_organizer`, so a second sender who copies a uid gets a different fact and can never shadow the organizer's. A missing SEQUENCE is 0 (RFC 5545) and a missing ORGANIZER means the sender. A first invite whose ORGANIZER is another address than its sender is written at confidence 0.5 (the on-behalf case, or a forgery of it); nothing but that sender can update it. An invite, its updates and its duplicates share one `fact_id`, and the reader's rule (latest source message, then the higher `ics_sequence`) picks the row; a JSON-LD event has no uid, so its id hashes the conversation key, sender, start, end and name, which makes a retitled or rescheduled JSON-LD event a second event, not an update.

**Updates and cancels (RFC 6047 iMIP).** A first invite from a trusted sender is accepted. A `CANCEL` (or `STATUS:CANCELLED`), and any later invite for an event already held, applies only if the event is held under that sender, the message names no other organizer, the uid matches and its `SEQUENCE` is greater than the highest stored (the event's rows and its applied cancels). A cancel then is a `fact` row with `links: [{relation: "cancel", target_fact_id}]` and no time, under one fact id for all cancels of that event; an update is a new row of the same fact with its new `when`. Anything else (a forged cancel from an invitee's domain naming the organizer, an update that ties the stored sequence but moves the time, a cancel with nothing stored, or any message naming another organizer than its sender) is written as an `event` fact with `review_reason: unmatched_update`, no `when` and no `links`, so it applies nothing and cannot move or hide the real event. Its id is the sender, uid, recurrence and kind (cancel or invite) and nothing of the message, so a flood of one forged cancel is one fact; calendar data naming another organizer than its sender is held under a separate id that is never read back. A duplicate delivery (same sequence, same time) writes nothing. An older invite of an event already held under the same sender (a newest-first backfill reads the older invite last) is the replay it looks like: it is skipped (`replay`) and writes no review row. Among the readings of one calendar event, the fold orders by SEQUENCE, not by message time: a skewed Date header neither hides a valid cancel nor lets an older update win.

**Order does not matter.** A backfill reads newest first, in batches, so a cancel can be read before the invite it cancels. An update read first is simply the first event stored, and the older invite then reads as the replay it is. A cancel read first is held (`unmatched_update`, under the sender's cancel id); when an event is written, the cancels held for it are read back and each whose sequence is greater than the event's is written as a cancel link, in sequence order, dated as the cancel's own message, with `source_event_id` and lineage of that message (not the invite), so deleting the cancel message removes it. A replayed cancel (sequence not greater) stays held. Within one batch messages are read oldest first. A cancel applied at sequence N also stops an update below N from bringing the event back.

**Times.** Resolved at write like `resolveWhen`. A UTC time is exact. A local time with a `tzid` that is an IANA zone (`Area/Location`, aliases such as `Asia/Calcutta` and links such as `Etc/GMT+11` included, via `usableZone`; abbreviations and offsets are not zones), or a common Windows name (CLDR `windowsZones`, `windows-zones.ts`), gets that zone's offset on that date (a skipped or repeated clock time is `ambiguous` with both readings). A `tzid` that is neither writes no event (`no_time`) rather than an event with no time. A zone-less (floating) time gets no reading and `ambiguous`: no zone is guessed. A `DATE` (all day) is read as the owner's calendar day in the owner's zone, `ambiguous`, one day long when there is no `dtend` (an exclusive end otherwise). A missing `dtend` writes a start with no end, and an end before the start is dropped. `TENTATIVE` sets `confidence` 0.5.

**Untrusted text.** The `SUMMARY`, the JSON-LD `name` and every other text field are never copied into a row (a fact holds closed values and offsets, never text) and never change an id or a row key, so a summary written as an instruction cannot reach a model or the reader; the owner reads the event from the source message. JSON-LD events are read only from mail the headers do not class as bulk or machine-sent (no `list_id`, unsubscribe header, `Auto-Submitted` or no-reply sender), skipped when marked `EventCancelled`, and need a `startDate`.

**Limits.** SEQUENCE must be strictly greater, so a cancel that repeats the invite's sequence (some clients do) is held for review. A recurring series is one event at its first start (the mail source does not report `RRULE`). `fact-ics` and `msg-class-t0` do not share a scan: each message is read once by each, so the summary's `derivedBehind` (a documented sum over extractors) counts a message once per extractor.

**Fold contract (2b-5 / 2b-7).** `open-facts-store.ts` maps `ics_sequence` to the fold row's `sequence` (the fold breaks ties between rows of one message time on it) and `review_reason` to `reviewReason`. `foldFactStates` then leaves a row with `reviewReason: unmatched_update` out altogether: it is never listed, never a link target and never the winner of its fact id. A cancel link row that carries an `ics_uid`, whose links are all `cancel`, and whose target is not in the read set (the event's message is older than the horizon, or was deleted) is an orphan and folds as a `link`, so a timeless cancel notice is neither open nor expired-open; a link row from the model extractor with a missing target stays a plain fact. A held `unmatched_update` is shown to the owner only as a review item: it never carries a time, because the row has none. The cancel link rows of one event share one `fact_id` and differ in `ics_sequence`, and the fold's one-row-per-fact rule applies to them unchanged.

**Model extractor hook.** `factIcsHandles(attrs)` (in `communication-readers`) is true for a message `fact-ics` takes over (trusted, and it writes at least one row). The model extractor of slice 2b-6 passes it as its `handledByFactIcs` predicate so the model does not read that message again; it is not wired here because that extractor is not on `main` yet.

**Known limit.** `msg_class` and `fact` rows must name `attrs.extractor` and `attrs.extractor_version` (rejected with the fix otherwise), but a holder of `write:activity-derived` can name any extractor, including the active one, so such tokens are trusted extractor writers; only `ingested_via` tells their rows apart. `writeDerivedRows` writes `msg_class` and `fact` only.

## The eval report

Labels are how extractors are measured against the person. He writes them from the owner session (chat or the app posting as him) with the generic ingest route: `{source: "derived", kind: "label", attrs: {source_event_id | fact_id, field, answer, slice?, stratum?}}`. No new tool or route: a token is refused `label` (owner-only) and `by` is server-derived, so a label counts only when `ingested_via IS NULL`; Mark's and tokens' labels are not read (the report shows how many it ignored). The `slice` is whatever the labeller asserts: the server records no draw, so "random" is the labeller's word, and a message labelled again keeps the slice of its earliest label. `stratum` is stored on the label and not yet reported.

`GET /api/activity-events/summary?report=eval` (`eval-report-store.ts`, one read-only repeatable-read transaction) returns, per active version and per other version with an `extractor_state` row (its `derived-shadow` rows): per-field precision (over labelled messages the extractor wrote a value for) and recall (random slice only), each with a 95% Wilson interval, a list such as `reasons` compared as a set; the wrong-auto-action count (a value the extractor wrote that he later labelled or overrode differently, his own word only; `source_gone` never counts; the first 50 are listed); and the T0 share (messages given a tier-t0 class, counted through lineage, over the raw messages still held, so deleted mail leaves both sides; a label about deleted mail is not scored and the entry says so). Facts (`fact_types` message labels, `[]` meaning none) are scored by `eval-facts.ts` from the version's fact rows grouped by `source_event_id`, not as a field: recall per type by membership (a message labelled {ask, deadline} and predicted {ask} is a hit for ask and a miss for deadline) over the random slice, with the positive count and a Wilson interval each, unadjusted for comparing four types; precision per type over every scored label; and, apart from recall, a false-alarm rate over the labelled-empty random messages (counts for every slice beside it). A labelled message is scored only when the extractor reached it: for the active version its position lies between the cursor's backfill and forward watermarks (compared by time, so millisecond and microsecond marks agree), for an inactive one its key is in `cursor.shadow.done` (a flat array of message event keys or row ids, oldest first; past 200,000 entries the newest are kept), and any message with a fact row counts. A message the runner skipped or is retrying (`cursor.skippedIds` entries with `id`/`key`, `cursor.retries` keyed by row id) is never reached, so the 2b-4 runner must keep those fields, and any `no_content` or T3-deferred marker, in the cursor while the message is unprocessed. When the fact window is cut short, a labelled message whose rows could lie beyond it (none read, or its oldest row at the window's edge) is left out too. The rest are `notReached` (neither a hit nor a correct negative) and the entry's `problems` says how many. A fact labelled under one version's id is found in another version, whose ids differ, by the same message and a span overlapping at least a quarter of the shorter one (containment, since a quote moves with the model's wording), paired one to one for the most total overlap (no span, no match; it also runs for a fact labelled with no message label). A promoted version has no numbers until it has processed labelled messages or shadow-run them: promotion leaves a window in which the report shows `notReached`, not a score, reported as `fallback.matched` and `unmatched`. `problems` on an entry names anything that makes it narrower than it looks. It says plainly that a few hundred labels show gross failure only. With `tokens_per_message` and `seconds_per_message` (both, bounded; refused with the limit otherwise) it adds `backfill`: the raw rows still held, the estimate (`estimateBackfill`) and the same with the T0 share taken out; without them there is no estimate section. The pure scoring, the seeded stratified sample plus random recall slice (`drawSample`, uniform over all candidates, labelled ones included) and the estimate live in `integrations/communication-readers` and import nothing else.

**Open facts (2b-5).** Which `fact` rows are still open is computed at read and never stored: `foldFactStates` / `openFacts` in `integrations/communication-readers/src/fact-state.ts` (pure) and `readOpenFacts` in `open-facts-store.ts` (one read-only REPEATABLE READ transaction, 15 s statement timeout; read by the attention feed, see Mark's read path below). Rules, each a named constant: several rows can share a `fact_id`, and the row from the latest source message wins (then the higher ICS `SEQUENCE`, then the key). An `ask` is closed by a later `from_self` message in the same conversation (not for an outgoing ask) and expires `ASK_HORIZON_DAYS` = 14 after the last message in the conversation; a `commitment` ages out the same way but only a status closes it; an `event` or `deadline` ends at its resolved time (the latest reading's end, else start, and an event with a start and no end runs `EVENT_DEFAULT_DURATION_HOURS` = 3 from it; an ambiguous time keeps `AMBIGUOUS_TIME_GRACE_HOURS` = 24 more) and, with none, expires `NO_TIME_HORIZON_DAYS` = 14 after its source message. A fact message later than the latest closing status (`done`, `cancelled`, `superseded`; not `source_gone`) reopens the fact: a repeated "Can you confirm?" after a `done` is a new ask. Statuses use the latest `valid_from` clamped to when the row was recorded (`ingested_at`), so a far-future `valid_from` cannot pin a status, and, on a tie, the person over Mark over an extractor. A person's status recorded after Mark's wins whatever its `valid_from` (Mark's statuses recorded before the person's latest are set aside, `afterPerson`); otherwise the latest `valid_from` wins. An override of the person's beats Mark's regardless of time; `by` is the server-derived `ingested_via` (null is the person, `extractor:*` an extractor, any other agent Mark). An `override` of `fact_type`, `when` or `direction` applies with the person's beating an agent's whatever the time, then the latest. Every time must be RFC 3339 with an offset and between 1970 and 2199, else it is ignored, so the answer never depends on the server's zone and no attr can make the fold throw. A fact row is dated by the earlier of its message time and when it was recorded, and a reply the same way, so a sender-dated future message cannot reopen a closure; a reply that is an auto-reply (`auto_submitted` present and not `no`) is not an answer. Links (`cancel`, `reschedule`, `repeat`) point at their `target_fact_id` and nowhere else: only a link that names no target falls back to the same `ics_uid`, else the only event or deadline, in the same conversation (several candidates means no link), and a named target outside the read set is an orphan. A link row with no resolved target is a plain fact and is listed; a link counts only when its target's message is strictly earlier than the link row's (so no loop is possible), follows a chain of at most `LINK_CHAIN_MAX` = 3 hops with the outermost relation, and is void if the person or Mark closed the link row. A `cancel` closes the target, a `reschedule` keeps it open at the new time (none resolved: no time, so 14 days), a `repeat` restarts the reply and age-out clocks. A status from the person or Mark beats a link only if it is newer than the link (then the link shows as `updateSeen`); an older one does not neutralise a later cancel. A reschedule moving a fact more than `RESCHEDULE_MAX_DAYS` = 366 past its own message is not applied (`updateSeen`), and repeats extend a fact's life at most `REPEAT_LIFE_MAX_DAYS` = 90 from its message in all. A resolved link row is never listed. Deleting the cancel message returns the event to open, and deleting the target orphans the link, which is ignored. `readOpenFacts` returns open and reopened facts, timed events and deadlines soonest first, then the rest newest first, with `total`, the horizon, `truncated` and the rows each read looked at. It reads only fact rows whose source message lies in `[now - horizonDays, now + 1 day]` (default 120, at most 366; at most `maxRows`, default 5000, newest first) through the `(user_id, source, ts_start)` index, so a three-year backlog is never walked, and a fact whose message is older than the horizon is not read even if its event is still ahead; `problems` always says so (counting those rows would scan fact rows with no index to serve it, so it is not done). Statuses and overrides are read from `(user_id, source, ingested_at)` from a day before the oldest fact read, filtered by `fact_id` with no index for those kinds (every derived row ingested in that range is looked at: fast, but proportional to a recent backfill); messages come from the thread index for the asks' and commitments' conversations only, without content. It is correct without the `fact_id` index of the 2b-2 migration, which it never uses. Measured on 4.5M rows (1.5M raw messages, 1.5M class rows, 200k facts, 2k statuses): 0.3 to 0.4 s warm at 30, 120 and 366 days. The ICS `SEQUENCE` tie-break is accepted by the fold but `readOpenFacts` does not yet supply it (fact rows do not carry it), so equal-time rows fall to the key.

**Mark's read path (2b-7).** Mark reads the open facts through `rhen_attention`, not a new tool or scope: `fact_open` items need `read:plan`, the scope the feed already needs (`portal/server/attention/fact-items.ts` over `readOpenFacts`; the owner view lists none, since no page shows them). A token without `read:plan` gets `notIncluded: [{kinds: ["fact_open"], scope: "read:plan"}]`; a failed or 10 s slow read is a `facts` source failure (a `soon` `source_unavailable` item, because the mail is optional and must not raise `counts.now`; `complete: false`), never a silent omission. Reads are shared between concurrent callers, a slow read stays the one in flight (no second beside it), and a failure is answered from memory for 45 s. Items are `soon` (a timed fact due within 48 hours, or an ask or commitment active in the last 3 days) or `fyi`, never `now`, so `counts.now` keeps its identity; `GET /api/attention?counts=1` carries `factsOpen`, the sum of the `fact_open` item weights (a fold counts its members; at most 200 facts are listed, so a larger backlog is counted as 200; a fact held by an open plan action is taken out before that cap, not after), `factsSoon` (the part listed as `soon`) and `factsFailed` (1 when the read failed; the counts are remembered for 30 s per person, so a plan save that holds a fact lowers `factsOpen` within 30 s, while the item list is always read fresh; never part of `sourcesFailed` or `now`). `rhen_status` shows an attention line when `now`, `decided`, `factsSoon` or `factsFailed` is above zero, so open mail that is only `fyi` never nudges. Ordering is its own: timed facts soonest first, then asks newest first, five kept and the rest folded with no tool to list them. A fact whose id sits, as a whole 40-hex token, in the notes of an open plan action (`fact_id:<id>`; not done, cancelled or archived) is not listed or counted, unless a mail came after that action was last updated; a closed action does not hide it (a commitment has no note field, so one saved only as a commitment is not matched). If the fact row cannot be found again to quote it, the item says so apart from a removed source. Only the five listed items read the mail: the quote is the fact's span resolved through `derived_lineage` to the message it came from, shown in `quoted.summary` with the sender in `quoted.title`, marked untrusted in the item's `why`; when the text is purged or the message gone it says `source_removed`, and when the text no longer hashes the same it says `source_changed`. `GET /api/activity-events?include=evidence` (limit 100 or less, which is also its default; it reads the message text as it is now, so it is refused together with `as_of`, with the call to repeat) puts the same on each `fact` row as `evidence` (`state`, `text`, `untrusted: true`, `note`; the text goes through the feed's sanitiser, one line of at most 200 characters) for a holder of `read:activity-event`. Reply closure reads only conversations the mail integration can thread (the store builds `conversations` from mail `conversation_key`s), so a reply in another source never closes an ask. An ask ages out 14 days after the conversation's last message even if the person confirmed it. A status can hold it longer through its `expires_at`, read only on a `confirmed` or `rescheduled` status, at most `STATUS_HOLD_MAX_DAYS` = 90 days after the status was recorded (a later value is cut to that, an earlier or invalid one is ignored; the write refuses an `expires_at` before `valid_from`, more than 90 days after it, or on another status, with the limit in the message). The call is `POST /api/activity-events {"source":"derived","kind":"fact_status","start":"<now>","attrs":{"fact_id":"<id>","status":"confirmed","valid_from":"<now>","expires_at":"<later>"}}` with `write:activity-event`; Mark's tools cannot make it until the 2b-9 mail room, so the item text tells Mark to save the ask to the plan (an action with the fact id in its note) only if the owner asks to keep it, never to write a status. A fact id is a sha1 of a sentence, the conversation key and the splitter version, and the row outlives retention, so a stock phrase ("can you send the invoice") is guessable by anyone holding the database or a backup; this is stated, not engineered (an HMAC would orphan every label on a restore without the key). Whether a person's status beats Mark's whatever the time is an open design question and stays in `resolveFactStatus`.

**Mark's marks (2b-9, room `facts`).** `rhen_inbox facts` lists the open facts (`GET /api/facts`, `read:plan`: id, type, due time, and for the first five only a sanitised quote, fenced as untrusted; the destructive call templates appear once in the list's header, never beside a quote, and only to a token holding `write:inbox`; the header sits inside the fenced untrusted result, so the rule that mail items need the owner's own words is also in `agent-policy-text.ts`) and the marks the agent can take back. `rhen_inbox_act {"room":"facts"}` posts to `POST /api/facts/[id]` with `write:inbox` (no new scope): `confirm` holds an ask or commitment open for 1 to 30 days (default 14) and never shortens the existing expiry; `done` and `ignore` (writes `cancelled`) close an item; `redate` moves an event or deadline within [message time, now + 366 days]; `reopen` takes back the agent's own mark only (it restores the extractor's `when` after a redate and will not resurrect an ask the owner answered or closed). `done`, `ignore` and `redate` need `basis: stated` with `evidence`, stored on the row (`attrs.basis`, `attrs.evidence`); closings are limited to 5 an hour and 15 a day per agent, all marks to 10 an hour, a hold to once a day per fact, and every real call (refusals included) to 120 an hour (a dry run is held to that limit but not counted); the limits count the `writes` receipts (type `fact_*`), which an undo leaves in place, so undoing and repeating never frees a place. The planner is pure (`planFactAct`); `actOnFact` runs one transaction: the 5 s activity lock (`lock_timeout`; a timeout answers "busy", nothing changed), the command receipt (`writes`, type `fact_<action>`, so a repeat with the same command id replays the stored answer and a refusal rolls back and leaves no receipt), a read of the fact tables under the lock, the derived `fact_status` or `override` row through `ingestActivityEventsTx` with `ingested_via` set to the authenticated agent, and a write snapshot (`fact_mark`, table `activity_events`: undo deletes the row, redo inserts it). `valid_from` is `now` taken before the lock wait, kept strictly above the fact's latest status. The mark therefore shows in Review > Agent changes and the Now agent-changes line, labelled with the item (type, due time, short id and a sanitised quote, or a note that the mail text is gone), where the owner undoes it. An agent may undo its own mark but not redo it: a redo of a `fact_mark` write is the owner's only. `fact_mark` snapshots have their own allowance of 2000 and do not count toward the ordinary 500. A `fact_status` or `override` row is written under the activity lock and stamped with the clock after the lock, whoever writes it, so recorded order follows commit order. The agent is the token's name: a caller with no token (the owner's session or a bare `X-OpenRhen-Agent` label) is refused, and a body naming `by` is a 400. A dry run reads the live fact and the agent's marks of the last day, applies the same limits and answers whether a real call would be refused, writes nothing, takes no lock and counts toward no limit. The listing (`GET /api/facts`) is read at most every 5 seconds per agent and is cleared by a mark, so a new mail or an owner's change can take up to 5 seconds to show; the room note tells the agent so. A mark is data about mail, not a plan change: it enqueues no recalculation.

Cost, measured on 4M rows (2M raw gmail, 2M `msg_class` with lineage, 465 label rows, the real indexes, 4 cores, Postgres 16): the whole report takes about 1.6 to 2.0 s warm and 4.0 s cold, no statement over 2.8 s, and 2.0 s with a backfill sizing. It is one pass over the person's `derived` rows of kind label, override or fact_status (no index on `kind`; 0.3 s warm, 0.7 s cold, parallel scan; it must be complete so no label is missed), indexed lookups for messages (event key) and their class rows (`derived_lineage`, under 0.1 s), fact rows by `fact_id` (exact, no window, the migration 0151 partial index) and by message key (the newest `window` fact rows of each `derived` source, `kind = 'fact'` inside the limit; no index on the message key; its `kind = 'fact'` and `source IN (...)` predicates are literals so a prepared statement keeps using the partial indexes), and the T0 share over the newest `window` raw messages by an indexed lateral lookup through lineage (1.2 s warm, 2.7 s cold). `window` defaults to 100000 and can be set from 100 to 1000000 (`?report=eval&window=20000`); an entry's `problems` says when it cut something off. Each statement runs under a 15 second timeout; one that outruns it is a 503 with `Retry-After: 60` and the fix (retry, or a smaller `window`), not a 500. The full scan of label, override and fact_status rows stays (no index on `kind` for those).
