# Desktop activity agent (rhen-watch)

Status: design for phase 1, Windows only. Owns: what the device agent in `tools/rhen-watch` captures, stores and shows, and the rules that bound it. The server half is the [activity store](activity-store.md); the uploader in this agent is a later change.

## What it is

`rhen-watch` is a small native program (Rust, two binaries, console and no-console, with a per-user `install` command) that records what happened on a computer so later features can compare the plan with the day. In phase 1 it is local-only: it writes a SQLite file on the machine (event rows are append-only; a per-minute input tally is the one exception, below) and has a command-line report. It sends nothing anywhere and has no network code.

## Rules

- **Observation only.** It reads. It never simulates input, steals focus, restores or closes a window, or opens a handle on another process (executable names come from a process list snapshot).
- **Unknown stays unknown.** A collector that is off or blocked writes nothing or an explicit `unknown` interval. A gap is never read as idle.
- **Opt-in for anything sensitive.** Collectors that read window titles, URLs, screen text (OCR) or images are OFF by default and are not built yet, and turning them on in the config is an error. Phase 1 on-by-default collectors record only the executable name, idle time, per-minute input amounts (never which keys or what was typed), session lock and display and power state.
- **Raw, not derived.** Rows are observed events. No derived label ("working", "in a meeting", a session, a block) is stored or written. `report` may compute and print derived facts (input blocks, switch rate, first and last input of a day) on demand, always marked derived and never written back; they are facts about input, not about a person, and nothing derived feeds the plan's energy or capacity figures.
- **Games are left alone, best effort.** The executable name is read from a process list snapshot, so no handle is opened on the game. While a denylisted executable is in front the agent writes one `suppressed` interval (without the name) and takes no idle samples or captures. The foreground hook stays registered and only forwards a window handle. Anti-cheat software such as Riot Vanguard may still object to hooks, so this is not a guarantee: before a game it has not been checked against, add its exe to `extra_games` or choose Pause in the tray (it persists across a reboot). The list ships with common anti-cheat games and is editable.
- **Never hidden.** It runs as the logged-in user with a tray icon, refuses to run as a service or in session 0, starts at logon only through `install`, and `stop` and `wipe --yes` end and erase it. Config defaults are compiled in, never read from a sample file.
- **No network.** No network crate is allowed in the dependency tree; CI fails if one appears.
- **Retention is settable, default permanent.** Local retention is set per data class (`retention.events`, `retention.metrics`, `retention.input_buckets`) in the config; `permanent` is the default and nothing purges unless set. A purge pass exists and is tested so a lower value works. Derived facts are recomputed from the rows, so a short event retention shortens what a report can derive.
- **No captured data in the repository.** Tests use synthetic events only.

## Collectors (phase 1)

| Collector | Source | Default | Writes |
|---|---|---|---|
| foreground | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` on a thread with a message loop | on | an interval per foreground exe: start, end, exe name, category |
| idle | `GetLastInputInfo` sampled every 5 s | on | idle intervals once the idle time passes a threshold (default 120 s) |
| input amount | the same `GetLastInputInfo` probe (no new syscall, no hooks, no Raw Input); follows `collectors.idle` | on | `input_buckets`: per minute and foreground exe, the time observed and the time with input, credited in 5 s slots; polled every 5 s, every 15 s while an idle interval is open, and not at all while paused, locked, suspended or a game is in front |
| session | `WTSRegisterSessionNotification` on a message-only window: lock, unlock, logon, logoff, remote connect | on | instant events |
| power | `RegisterPowerSettingNotification` (AC/battery, display on/off) plus `WM_POWERBROADCAST` suspend and resume on a hidden top-level window | on | instant events |
| title | `GetWindowText` of the foreground window | off | title on the foreground interval |
| ocr | `PrintWindow(PW_RENDERFULLCONTENT)` then Windows.Media.Ocr, on window change and every N seconds while unchanged | off, step 2 | text row; minimised windows are skipped, images never touch disk |

OCR and title are built after the local-only core is verified on a real machine; this change builds the first four collectors plus store, report and metrics, then OCR in a second change.

**Foreground details.** The hook is out-of-context, so the callback only posts the window handle to the agent's own channel; lookups happen off the callback. De-duplicate repeats of the same exe. Ignore shell windows by class (`Shell_TrayWnd`, `Shell_SecondaryTrayWnd`, `NotifyIconOverflowWindow`, `XamlExplorerHostIslandWindow`, `TaskSwitcherWnd`, `ForegroundStaging`) so a tray click does not end the app interval. `LockApp.exe`, the lock screen, is ignored by executable name whatever its window class, because it belongs to the lock and is not app time. For `ApplicationFrameHost.exe`, resolve the real app from child windows after a 300 ms delay and re-check once. Every Electron app shares the class `Chrome_WidgetWin_1`, so identity is the exe name. Its category comes from the per-exe map in `categories.toml` beside `config.toml`: shipped defaults are compiled in and the file holds overrides (`[exe]` exe to category, `[group]` category to group), and it is the only home for them (a `[categories]` table left in `config.toml` stops `run` and `report` with a one-line message to move it). Categories fall into coarse groups (`work`, `browser`, `comms`, `media`, `play`, `other`) used only for derived input stretches. An exe in no table is written as `other` but is listed by `report` as not categorised yet, and `report` re-resolves categories from the current map when it prints, so labelling an exe relabels history in the report only. A bad `categories.toml` fails `report` with file, line and reason, while `run` logs it, writes one `agent/degraded` marker and records with the built-in categories.

**Intervals cannot lie.** A row in `events` is written once, when its interval closes, and never changed. `input_buckets` is not an event table: it is a per-minute tally exempt from the write-once rule, written by idempotent upserts keyed by (minute, exe, run) and removed only by retention. The tally is written on every poll, so a crash loses less than one poll interval of it, and `run` (a tally generation bumped by every reset: start, pause, resume, lock or suspend and their release, stall, clock jump, entering or leaving a game) means a restart or a wall clock stepped back adds to earlier values instead of overwriting them; readers sum over `run`. Intervals still open live in memory and are mirrored to `meta.open_state` with the heartbeat in the same transaction as every batch, so they survive a crash. At start the agent closes any such interval at the last heartbeat and records the time it was not running. A clean stop writes a `clean_stop` marker in its final write, equal to the last heartbeat, and the next start clears it. If the marker matches, the time is recorded as `off` (reason "agent stopped") and the console says nothing. If not (a crash, a kill, a power cut), it is recorded as `unknown` and the console says the previous run ended without a clean stop. The `agent/start` row carries the settings of the run: `idle_threshold_secs`, `collectors`, `retention`, `extra_games_count` (a number; the game names themselves are never stored) and `categories` (`file`, `default` or `degraded`). While running, a gap of more than 30 s between one-second ticks (sleep with no suspend message, a frozen machine) closes everything at the last tick and records the gap as `unknown`; a wall clock that moves backwards closes at the earlier of the old and new times and records `clock_jump`. Suspend and resume also arrive through `RegisterSuspendResumeNotification`. Signals dropped because the bounded channel was full are counted and recorded as `dropped` (not while paused, when only the count is kept), then the lock and remote state are read from the session (in the same tick, before the idle probe) and the foreground is read again, so a lost unlock cannot hold recording off. The same read happens once at start, so an agent started while locked or over Remote Desktop records `locked` or `remote` from the first moment (`WTSQuerySessionInformationW` with `WTSSessionInfoEx`, and `GetSystemMetrics(SM_REMOTESESSION)`). A wall clock that moves backwards while locked, suspended, remote or display-off reopens that interval at the new time instead of dropping it. The queue is drained before the re-read after a drop, so an older queued lock cannot overwrite the state just read; an unknown lock flag still lets the remote flag sync. Durations come from the wall clock; a skew that the tick check cannot see is a known limit.

**Threads.** One hook thread owns a hidden top-level window (message-only windows do not receive suspend and resume) and the message loop; callbacks only try-send into a bounded channel. The main thread drains it, runs the engine, and writes. A panic is caught, open intervals are closed, and Ctrl+C, console close, logoff and shutdown all request a clean stop. A second instance is refused by an exclusive lock file that the OS drops if the process dies. The stop event is created with the default security descriptor, so only the creating user can signal it.

## Storage

SQLite in WAL mode (with `secure_delete`) at `%LOCALAPPDATA%\rhen-watch\activity.db`. On first run the folder's inherited permissions are removed with `icacls` so only the current user (not Administrators or SYSTEM inheritance) can read it, including the WAL and SHM files. A network-share path prints a warning. Tables: `events` (id TEXT primary key generated on the device, device, ts_start, ts_end, source, kind, attrs JSON, tz_offset_min), `input_buckets` (minute_ts, exe, run, observed_ms, input_ms, tz_offset_min; `WITHOUT ROWID`), `metrics` (per-minute CPU time, working set, database size, event and drop counts), `meta` (schema version, device id, heartbeat, open state, pause flag, run sequence). `tz_offset_min` is the local offset east of UTC in minutes when the row's time began (an interval keeps the offset it opened with), so an upload can send each event's own local time; it is NULL for rows from before version 2 and for times more than 5 minutes before they were written, such as the gap recorded after a crash. The schema is version 2; moving from 1 to 2 is one-way (an older agent refuses the file), and the read-only `report` accepts both. The id exists before any later upload, so a future uploader is idempotent. Writes are one transaction per batch.

## Tray, pause and install

The agent shows a tray icon whenever it runs (it is never hidden). Its menu has Pause or Resume, Open settings and Open data folder (both open the data folder, which holds `config.toml` and `categories.toml`) and Quit; nothing in it touches any other app. The icon is a built-in Windows icon that follows the state (recording, paused, degraded), and a balloon appears once when writes start failing. Adding the icon is checked: if the shell refuses at logon, the agent retries every 2 seconds, and a failed update falls back to adding it again. Pause closes every open interval and records a `paused` interval; nothing else is recorded until resume, not even gaps, and the paused state is stored so a restart stays paused. `rhen-watchw.exe` is the same program built for the Windows subsystem so start-at-logon shows no console; `rhen-watch.exe install` copies both to `%LOCALAPPDATA%\Programs\rhen-watch`, sets an HKCU Run entry and starts it; `uninstall [--purge]` reverses it. It is a per-user app, not a service, because the foreground hook and lock state exist only in the interactive session. A failed final write at clean stop is reported, not swallowed. `install` warns when run elevated (an administrator agent cannot be stopped from a normal prompt, and `stop` says so when it meets one; it is a warning because CI runners have no normal prompt) and validates `config.toml` before it copies anything or sets the Run entry. A failed per-minute metrics write is logged once per spell and retried each tick, and a failed daily purge once a minute, both with a short (100 ms) wait on a locked database so a tick is never stalled for the event writes' 5 s wait; neither can end the agent. What can end it: 60 event writes in a row failing, the hook thread ending, or `run.start` / `stop` failing. If `run` fails before it is recording (including a panic outside the recording loop), the no-console build shows the error in a plain message box ("did not start"), and the same for a `run` that ends with an error after recording began ("stopped"); a duplicate start gets no box. The box is shown after the run lock is released, so a new agent can start, and it closes itself after 60 seconds so it cannot hold the program file for an install; what it does to keyboard focus has not been checked on a real PC and is not claimed.

## Interface

`rhen-watch run [--for SECONDS]` runs in the foreground until Ctrl+C, `rhen-watch stop` or the time limit; it unhooks and flushes on exit and on panic. `rhen-watch report [--day YYYY-MM-DD | --from YYYY-MM-DD --to YYYY-MM-DD]` prints "your day at the PC" first (derived: first and last input, input against time in front, the longest unbroken stretch, input blocks, switch rate, exes not categorised yet), then time per app and category, idle and locked time, paused time and time the agent was off (each its own line), `unknown` gaps, a count of instant events (logon, power source, start and stop) with any backwards clock jumps, and the collectors' own cost. Paused and off time count as known in the day's partial check, and only records that start inside the day set where its recorded part begins, so an overnight shutdown does not make the day partial. A day is local midnight to the next local midnight, each end with its own offset, so the days DST changes are 23 or 25 hours. `rhen-watch status`, `config init|path|show|set KEY VALUE` (`set` validates the same way a loaded file is, keeps the file's comments and writes atomically), `categories init [--from-config]|path|list [--uncategorised]|set EXE CATEGORY`, `rhen-watch export PATH` (a consistent copy of the database through `VACUUM INTO`, safe while the agent runs, never overwriting), `config init|path|show|set KEY VALUE` (`set` validates the same way a loaded file is, keeps the file's comments and writes atomically), `categories init [--from-config]|path|list [--uncategorised]|set EXE CATEGORY`, `wipe --yes` (database, sidecar files, config and the two log files; `uninstall --purge` also removes the data folder when it is then empty). The numbers the derivations use are the `[derive]` settings. The portal's settings page (Wave C) will carry the same settings and must reuse these keys and their validation rather than invent a second schema.

## Budget (to agree with the owner)

Under 1% of one core on average and under 50 MB working set for phase 1, measured by the agent's own metrics over a normal day. The spike numbers are PowerShell numbers, so no Rust figure is claimed until measured.

## Server half

The server side is built and documented in [Activity store](activity-store.md): `POST /api/activity-events` (scope `write:activity-event`, preset `activity-capture`, header `X-OpenRhen-Token`), the append-only `activity_events` table (migration 0148), per-source content gate and retention, and the read-back route. It adds no MCP tools (the `tools/list` budget is capped), and `portal/server/watch-history/engine-blind.test.ts` keeps the engine, scheduler and pulse from reading the tables. The uploader in `rhen-watch` is not built yet. When it is, each local event posts as `source: "rhen-watch"` with the local kind as `kind`, the local `id` as the event key (so retries are idempotent), the device id, and `tzOffsetMin`. Titles and OCR text are `content`, stored only when the owner turns the gate on for `rhen-watch`.

## Tests

Pure logic is tested on Linux and Windows runners: interval building, de-duplication, the shell-class filter, game suppression, stall and clock-jump handling, crash recovery from the open-state record, retention purge, the report, config parsing and `config set`, `categories.toml` parsing and edits, the input meter (credit by input instant, caps, minute splits, every reset path), the derivations (sessions, input blocks, switch rate, day edges), local-day windows across daylight saving (a Pacific/Auckland fixture: 23 and 25 hour days), schema migration 1 to 2, and a simulated day through the runner with a fake OS. The Windows API layer is behind a trait and is compiled and linted on `windows-latest`; its behaviour is confirmed by the manual script in the tool's TESTING.md, which is observation-only. The `windows-latest` job installs the real binaries, checks that the agent records, installs again over the running copy, kills it and restarts it to see the unknown gap, exports the database, and checks that `uninstall --purge` removes the data folder.

## Releasing

Bump `version` in `tools/rhen-watch/Cargo.toml`, merge, then push the tag `rhen-watch-v<version>` (it must match exactly; `scripts/ci/rhen-watch-version.mjs` refuses otherwise). `.github/workflows/rhen-watch-release.yml` builds the Windows zip on a hosted runner, writes one `SHA256SUMS` over every archive, stamps `scripts/install/rhen-watch.ps1` as `install.ps1`, and creates the GitHub Release; only its last job has write access. Running the workflow by hand with a tag input is a dry run that uploads the assets as a workflow artifact and releases nothing. Releases are unsigned.

## Known limits (phase 1)

- The lock flag is read through `WTSSessionInfoEx`, whose lock and unlock values Windows 7 and Server 2008 R2 return swapped; those versions are not supported. If Windows will not say, the agent keeps what it has been told by signals.
- A suspend whose resume message is lost would leave the `suspended` interval open until the next resume or stop.
- `rhen-watch stop` uses a per-logon-session event, so a remote desktop session cannot stop an agent running in the console session; use Ctrl+C there.
- Store writes that fail are kept in memory and retried each second; the agent exits after about a minute of consecutive failures.
- Pause drops any lock, remote or suspend state in progress and ignores their signals; resume reads the lock and remote state from the session again (then the foreground), so a lock that is still on is recorded from the resume. A suspend that began before pausing is not restored.
- `SM_REMOTESESSION` is assumed to clear after a Remote Desktop disconnect; check this on a real PC, as a resync would otherwise reopen `remote`.
- Retention purge runs on the first tick of each UTC day, then shrinks the write-ahead log.
- Synthetic input (remote tools, jigglers, scheduled tasks) is counted as input and cannot be told apart; every printed input figure says so.
- Input is credited in 5 s slots (at most 5 s per poll with input), so it is a lower bound; reading, watching and any input-free activity look like a gap, and a session is only as long as its input.
- A machine with no input at all for 49.7 days can alias the 32-bit tick counter and read a small idle time; unlock and boot are input, so this needs an untouched machine.
- Derived facts are recomputed from rows: a short `retention.events` removes the interruptions they are read against, and `report` then says "partial: events purged" and prints no facts for that day rather than glue sessions across purged locks.
- A first input is the first minute with enough input, not a wake time or a presence claim; nothing derived here feeds energy, capacity or any wake estimate.
- Local-day offsets come from `SystemTimeToTzSpecificLocalTime(NULL, ..)`, which applies the current year's daylight-saving rules to every date; a day before a rule change gets the wrong offset (and window).
- Retention is checked against the oldest event still stored: input rows older than it are read as unknown and never joined into a session, and the day is marked partial.
