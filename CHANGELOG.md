# Changelog

All notable changes are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow semantic versioning once 1.0 is released.

## [Unreleased]

### Added

- **Each source's own rhythm decides late and stale**: a source that reports coverage is no longer judged against 12 h and 24 h. Its limit T is learned from the gaps between its own coverage posts (the larger of 3 x the median gap and 1.5 x the second-largest gap, at least 5 minutes), so nights, weekends and a single outage do not make a healthy source look stale; it is late at T and stale at 2T. A late provisional source makes `planInputs.complete` false without blocking, a source with too few updates for a rhythm that has not posted for a week gets a tidy note, the owner's expected rhythm is refused for a source that never reports coverage, and backups are now format 27 (a format 26 backup restores the column as null). A limit from 2 to 5 gaps, or from less than max(24 h, 4T) of history, is provisional and never blocks the plan; a source with fewer than 2 gaps and nothing declared has no number and nothing is called late. A collector's declared cadence is real from day one and holds what blocking learns to 4 x it. A source more than 3 x its stale limit and at least 7 days behind (the abandonment floor, not a staleness limit) is treated as retired and stops blocking. The owner can say how often they expect a source: `PUT /api/activity-sources/:source` takes `expectedEveryMinutes` (5 to 129600, `null` clears it; T = 3 x that) and `rhen sources <id>` shows the limit and where it came from. Migration 0154 adds `activity_source_state.expected_every_minutes`. The older mail source counts as changing the plan once its collector reports coverage.
- **Answered check-ins: cursor paging, filters and `rhen check-ins`**: `GET /api/check-ins/answered` gains `next` in its result and `?cursor=` to send it back: paging on (answer time to the microsecond, id), it neither skips nor repeats rows that share an instant, which `?before=` (a timestamp only) can. `cursor` with `before` is a 400 that says to send one. `?untagged=1` keeps check-ins with no tag and `?with-words=1` those with non-blank words (1, true, 0 or false; anything else is a 400 naming the fix). The existing fields, order, `since`, `before` and `limit` (default 20, at most 100) are unchanged. The new CLI command is `rhen check-ins [--since] [--before] [--cursor] [--limit] [--untagged] [--with-words]`; it is not on the remote `/mcp` list, whose size budget has no room, and the agent contract version is unchanged. No setting, no migration. Overlay-impact: Seam: agent routes. Change: one optional response field and three optional query parameters on an existing read route, one CLI command. Version bumped: none. Add-ons affected: none. Migration needed by add-ons: none.
- **Answered check-ins read (`GET /api/check-ins/answered`)**: lists answered check-ins newest first with their ids, status, the owner's words (`deviationNote`), tags, `answeredAt` and `answerSource`, voluntary ones included, so a reader can find a check-in to tag. `?since=` and `?before=` (ISO 8601, on the answer time) and `?limit=` (default 20, at most 100) page it; owner auth, or an agent token with `read:plan`. No MCP or CLI tool, no setting, no migration. The answered-check-in tags and the private "What pulled you off?" tags stay two stores (see [Drift](docs/architecture/drift.md#check-in-words-and-tags)).
- **Words-first check-ins**: a check-in answer keeps the owner's own words on every status (`deviationNote`, now up to 8000 characters, on `on_track` and `unknown` as well as `deviated`; `rhen check-in --note` and `rhen_check_in` `note` follow). The check-in sheet and the session reconciliation panel no longer ask for a category; `deviationCategory` is still accepted from older callers. `answerSource` gains `widget`, `shortcut` and `app`, and `push_action` (until now only in the database) is accepted by the command schemas. New open tags on an answered check-in, `[{tag, mark}]` with `mark` `stated` or `inferred`, written by a reader through the new `tag_check_in` command (`rhen check-in-tag`, MCP `rhen_check_in_tag`, scope `write:check-in`): it adds or removes tags only and never changes the status, the words or the pulse. Migration 0153 adds `check_in.tags` and widens the answer-source check; the column rides inside `check_in` in backups, so there is no format bump and an older backup restores with no tags. The agent contract version is now 12 (a new tool); `rhen_check_in`'s deviated answer no longer needs `category`, and the check-in wake asks for the owner's words as `note`. No setting. Overlay-impact: Seam: agent tools. Change: one tool added, `rhen_check_in` no longer requires `category` on deviated. Version bumped: agent contract 11 -> 12. Add-ons affected: unknown. Migration needed by add-ons: none.
- **rhen-watch 0.2.0: a Windows app**: `install` adds a Start menu entry, `rhen-watch`, that opens a settings window (also the tray's Open settings, and what `rhen-watchw.exe` does with no arguments). Overview shows whether it is recording, paused or not running (and why), with Pause or Resume, Stop, Start and today's report; Apps sets a category for apps that have none, through the same code as `categories set`; Settings has Start with Windows, how long to keep data (a shorter choice says how many events it would delete and asks first) and the idle threshold. It is a separate process from the recorder, talks to it through its hidden window and the stop event, and has no network code and no server setting. The tray now uses three generated icons (green, grey, amber), the agent keeps its state in `state.txt`, and `install` and `uninstall` close an open window first. `install` also puts its folder on your user PATH (no admin; `uninstall` removes only that entry), so `rhen-watch` works from a new PowerShell. Upgrade by running the installer again; an agent started by 0.1.x shows as running but cannot be controlled from the window until it is restarted. No setting, no migration.
- **Client view (`GET /api/client/view`, native app C2)**: one owner read for an installed app and its widgets, `?parts=now,day,pending` (default all three). `now` is `buildNowAnswer` and `day` is `buildDay`, the functions the web and `rhen status` use; `pending` holds the waiting check-in, the active session, the leave-by leg and a phone place suggestion. The `ETag` covers the whole body and `If-None-Match` answers 304; instants are ISO 8601 with an offset. The check-in is read with `stamp: false`, so a widget or background refresh no longer starts its timeout; the new owner-only `POST /api/check-ins/{id}/shown` stamps `prompted_at` once (idempotent) when a surface actually shows it, and the timeout still runs from `prompted_at ?? created_at`. Both routes are owner-only (an agent token is refused) and open to a limited device credential. The types are exported as JSON Schema (`platform/contracts/client-view-schema.v1.json`) with a fixture per type (`client-view-fixtures.v1.json`), checked current by a test. `GET /api/device/now` is unchanged. No setting, no migration. See [Client view](docs/protocol/client-view.md).
- **Device sign-in (add a phone)**: Settings > Sign-in and devices gains **Add a phone** (a QR holding the portal's public origin and a ten-minute, single-use pairing secret) and **Enter a code** (an RFC 8628-shaped fallback; the owner types the code, there is no approval link). New routes `POST /api/owner/devices/pairings`, `/redeem`, `/code`, `/code/token`, `/code/approve` and `POST /api/owner/web-session`, and `GET /api/owner/credential-events`. A phone gets its own revocable kind-`token` owner credential that is **limited** (new class `owner-admin` in the route table: no enrolling, minting or revoking others, pairing, saved keys, connection setup or source purge; every other classified route works and an unclassified one is refused). The web-view cookie is a child of the device credential, inherits `limited`, is revoked with it, sits outside the browser cap and is reused per device. `POST /api/location/ping` also accepts the device's owner header token (never a cookie) and an optional `device`, and tracks sustained presence per device; `LOCATION_PING_TOKEN` is unchanged. Pairings, redemptions, approvals and revokes are recorded (migration 0152: `owner_credentials` gains `device_install_id`, `platform`, `limited`, `parent_credential_id` and `last_used_from`; new tables `owner_device_pairings` and `owner_credential_events`, neither in backups). See [Auth per seam](docs/protocol/auth.md#adding-a-phone-device-sign-in).
- **Mail file importer**: `rhen import mail <path> --source <name>` posts standard `.mbox` (mboxrd/mboxo) and `.eml` files as `message@1` events into a source you register, keyed `mid:<Message-ID>` (else the `fp:` rule), text kept, duplicates across files dropped by `Message-ID`, streamed with a per-message size cap, and stopping with the file, message and byte offset on anything it does not recognise. Built from the standards and tested on synthetic files only.
- **Drift source and work labels**: a new activity source `drift` (kinds `work_label` and `flag`; owner-only to write, no token scope opens it, and a token reads it only with the new `read:activity-drift` scope, kept out of the default OAuth grant). Your local model infers whether an area counts as work from its public text (private areas, private projects and private actions are never sent), and the area page shows it with Yes, No and Reset taps that record your own answer, which wins. New owner routes `GET /api/work-labels`, `PUT /api/work-labels/[areaId]` and the worker's `POST /api/integrations/work-label/tick`; no new MCP tool and no setting. Nothing sends a flag yet.
- **"What pulled you off?" in the check-in sheet**: when you answer a check-in as "Something else", an optional text box lets you say why in your own words. It is saved by its own owner-only route before the sheet closes; if the save fails, your words stay in the open sheet with Try again and Skip. The words go to a new activity source `drift-reason` (kinds `reason`, and `reason_tag` for tags a later change adds) that no token can read or write and that no generic activity listing shows. Retention never applies to it, and `DELETE /api/drift-reasons/[checkInId]` removes a reason and its tags. New owner routes `POST /api/drift-reasons` and `DELETE /api/drift-reasons/[checkInId]`; no new MCP tool, no setting, no migration. The reason is separate from the Note, which still means what you did instead.
- **Neutral message contract (`message@1`)**: a family for messages from any mailbox, chat or notification feed, posted by your own collector. Kind `message`, closed attrs (`message_id`, `from`, `to`, `from_self`, `direction`, `channel`, `thread_id`, `subject`), a canonical key (`mid:<normalised id>` or `fp:<hash>`) and a server-computed content fingerprint `attrs.fp` taken before the content gate. Contract only: the store does not yet compare fingerprints across sources, and the existing mail source is unchanged. A coverage row's `attrs.scope` now also refuses control, zero-width and text-reordering characters and `:` (it is still compared exactly, so `Inbox` and `inbox` are two scopes), and message text fields refuse the same hidden characters. See [Posting messages](docs/operations/posting-messages.md).
- **Whereabouts class and scopes (registry groundwork for places)**: sources can now be of class `whereabouts` as well as `health`, each read with its own scope. New scopes `read:activity-whereabouts` (read whereabouts rows) and `write:place-model` (write the owner's place model); neither is offered to OAuth clients. `GET /api/activity-events` adds `withheldClasses` (a count per class) beside `withheld`, and the `withheldNote` now names the missing scope for each class. No source is of the new class yet, so nothing is withheld that was not before. Registry entries can also declare positions, external place ids and place hints as data.
- **Data-flow registry for composed builds**: a health probe may name a table as `schema.table` (each part a plain identifier, the table must exist in the catalogue, each part quoted separately); the write-evidence scan reads schema-qualified `INSERT`, `UPDATE` and `DELETE`; a tool an extension adds may carry `commandFile`, so the surface check reads its command as evidence; and the extension-seam test no longer assumes it is the only registered extension.
- **Per-device view of health data in the activity summary**: the owner's `GET /api/activity-events/summary` gains `devices`, one entry per device, kind and collector (token name) for `physiology`, `apple-health` and `iphone-health`, with the last event, the last ingest and the row count of the last 30 days. It is read from the stored rows in one bounded indexed scan (timed at 100k rows in the tests); no counters, staleness judgement or doctor items are added. To keep reading `apple-health`, `iphone-health` and `physiology` rows over a token or connector, grant it `read:activity-health` as well as `read:activity-event`. No migration.
- **The Data page (`/data`)**: a live map of every data point from the registry and `GET /api/data-flow`: outside systems and devices, collectors, stores, readers and what each gives, with status, age, reach to the planning engine, filters and a drill-down panel per node. It polls every minute while visible, says "Health unavailable" over the last graph if the read fails, and becomes a problems-first list under 720 px. Read-only, no migration, no setting. The counts line links to it from the You and Connections headers. See [Settings and connections](docs/product/settings-and-connections.md#data).
- **Physiology schema and endpoint (activity store)**: a generic source `physiology` with 14 period-row kinds (heart rate, dense heart rate, HRV, stress, named score series, respiration, SpO2, skin temperature, steps, movement, sleep, daily, score, workout) that any wearable, phone or health app can be mapped onto, posted by your own collector to the existing `POST /api/activity-events`. Every row has one canonical key, `<kind>|<device>|<period>|v<v>`, that the server checks and states when wrong, so the same fact from two routes has one identity; every rejection names the field and the fix. A fuller re-post of a period is stored as the next `v`, and the ingest response's new `held` list says what is already stored for a key you re-posted. The shape is published as `platform/contracts/physiology-schema.v1.json` ([Posting physiology data](docs/operations/posting-physiology-data.md)). Core has no poller, adapter or provider key, and physiology never changes what the plan allows. No migration.
- **Health scope for reading activity back**: new scope `read:activity-health`, added to an agent token with `rhen agent-token create --scopes read:activity-event,read:activity-health`. It is deliberately not offered to OAuth clients, so a default connector grant never includes it.
- **Data-flow registry and `rhen sources`**: a typed registry of every data entry point (collector, shared pipe, reader, sink), checked against the code in CI, with a live health signal per node. `GET /api/data-flow` returns the graph and health (read-only, scope `read:plan`); `rhen sources [id] [--problems] [--unused] [--json]` prints it, and `--offline` builds it from the code alone. Stdio MCP only, so the remote tool list is unchanged. Without a database the route answers 503; if the probes fail, `health` is `{ unavailable, reason, next }` with a fixed reason. The `physiology` source and `wearable` device are registered (accepted, nothing sends yet). See `docs/architecture/data-flow-registry.md`.
- **Doctor source checks**: `rhen_doctor` now also reports a data source that has gone quiet (or one kind of it), a token that has never been used, a device whose feeds have all stopped (one item, not one per feed), a registry entry whose health cannot be read, rows arriving into a feed nothing uses, and a file import that skipped rows. Calendar sync items are unchanged. The Data check and Connections headers show the counts ("4 late · 1 device silent · 11 collected, unused"), and the health reader now bounds each probe with a statement time limit, and names a quiet kind per source. The probes also run on one read-only connection under a 15 s overall deadline, and a learned threshold can make an item blocking once a source has a month of history. Driver error text never reaches an agent or the page: probe failures show a fixed reason and go to the server log. Agent fixes carry a new `fix.next` step in words. No migration and no new setting.
- **Comparison-based consequence (storage and refit)**: new tables `consequence_comparisons` (the append-only log of ranked groups) and `consequence_groups_issued` (every group handed out) and nullable `consequence_refined`, `consequence_refined_for_stars` and `consequence_refined_as_of` columns on projects and actions (migration 0150). A refit recomputes the refined values from the log whenever an answer is recorded, inside every whole-state replace and import commit, after a restore, and when a plan is built on a new day; stale answers (changed stars, title, definition of done, deadlines or parent) and finished items drop out at fit time, and a failed refit leaves the previous values. Backups move to format 25 (formats 24 down to 20 still restore, with the two tables empty). Nothing asks for or records an answer from the portal, CLI or an agent yet, so ranking is unchanged until it does.
- **Run rows for silent paths**: file imports, rejected activity events, the travel and plan-map ticks and the handheld's polls (accepted and refused) now leave rows in `integration_sync_runs` under `import:`, `ingest:`, `job:` and `device:` providers (no migration; the table already takes these). `rhen import` posts one run per source to the new `POST /api/activity-imports/runs`, keeps going when one source fails, and exits non-zero at the end if any did. The doctor's sync check ignores these providers. Nothing shows the rows yet. See [Activity store](docs/architecture/activity-store.md).
- **Comparison-based consequence (ranking by hand and by agent)**: `rhen rank` shows the next group of four projects (or four actions of one project), numbered, with the question for the day, and takes the order as numbers, `--tie` or `--skip`. The two questions ("If you could only get one of these done, which would you do?" and "A year from now, which of these would you most regret never having done?") alternate by your local calendar day. The same server command, `POST /api/commands/consequence`, answers a group for the portal and for agents; `GET /api/consequence/next` hands the group out. An agent reads the group from `rhen_inbox` with room `compare` (never a private item) and answers with `rhen_save` entityType `comparison`, under the new scope `write:entity:comparison`; a person's answer counts in full, an agent's `stated` and `observed` answers need evidence and `inferred` counts for half. A wrong group is refused with the group that is waiting and the exact next call. Each answer refits and recalculates, so Now reflects it. The tool list grows by 169 bytes (core 107,287 to 107,456 of 108,500): the `rhen_inbox` description gained one sentence about room `compare`, and the `rhen_inbox` room enum and the `rhen_save` entityType enum each gained a value. A group that holds a private item is refused to an agent as if it had never been issued, without naming the group or its ids.
- **Comparison-based consequence (the "Rank these four" card)**: Plan has a small card below the areas that asks the day's question about four projects (or four actions of one project), shown with stars and parent. Drag them into order, or use Move up and Move down, then Submit order; "These are equal / can't decide" records a tie and Skip records a tie with the evidence "skipped"; the fit ignores ties, so neither moves a ranking. A confirmation line, a per-device count (today and this week, with the note that every answer is optional) and a soft "A few more" prompt after three groups in a day come with it; an empty queue says why and what to add, and a refusal shows the server's message. No setting: it ships on, and it reads nothing until opened.

- **Takeout downloader**: `scripts/ops/takeout-download.ps1` fetches every zip part of a finished Google Takeout by replaying one browser download request, skipping parts already saved.

New activity sources `timeline`, `google-chat`, `google-access-log` and `google-photos`. - **Now offer log records what was shown**: the open Now page (when it is visible) and the handheld (when its screen changes) now add a `shown` row naming what Now resolved to, and the engine primary it covered when something else (a commitment, sleep, a routine step) was on top. `shown` is a lower bound on what you saw: background tabs, several surfaces and polling can miss or repeat exposure, and an identical repeat within five minutes is dropped. - **Data-export importers (`rhen import <source> <path>`)**: load a Google Takeout (Chrome history, My Activity, Maps places, Fit steps, and YouTube history through the existing watch-history import), a Spotify extended streaming history, a Discord data package or an Apple Health export into the activity store from the command line. The export is parsed on your computer by the new `integrations/activity-importers` package (streaming, so multi-gigabyte zips are fine) and only parsed events are posted, in batches, to `POST /api/activity-events`; rows it cannot read are skipped and counted with their reason, and a file already imported is not sent again. - **Passwords and keys, and video lengths for watch history**: a new **Settings > Passwords and keys** page takes a YouTube Data API key, saved encrypted (AES-256-GCM under a master key, write-only, never shown back and unreachable by any agent route or tool), and Review then looks up each watched video's length through the outbound proxy (new `youtube_data` connection, `video_metadata` capability) to narrow the time estimate. Adds migration 0146 (`app_secrets` and `youtube_quota_use`, both left out of backups, so no backup format change) and the environment variable `OPENRHEN_SECRETS_KEY` (32 random bytes, base64, portal only; `init-env` makes one). - **The agent is woken when attention items appear**: when a blocking data-health item or a due catch-up shows up after the feed was empty, the worker sends the agent one `[OpenRhen wake]` message (at most one an hour, none while the owner is asleep, cancelled if the feed is read first), so it no longer waits for someone to look. Adds migration 0144 (one more `agent_wakes` event); no new tool text.
- **I'm free**: say you are free of a running commitment (the Now button, `rhen free <id>`, or an agent saving `free: true`) and the planner recommends your next task at once, without ending or moving the commitment. Undo restores it. An agent's request on a commitment shared with the family calendar waits for your confirmation. Adds the nullable column `commitments.freed_from` (migration 0143, additive).

### Changed

- **Health rows are withheld from tokens without the new scope**: `GET /api/activity-events` now leaves out sources of class `health` (`apple-health`, `iphone-health` and `physiology`) for a database token or connector that holds `read:activity-event` but not `read:activity-health`, and names the withheld sources and the missing scope in the page's `withheld` and `withheldNote`. Existing tokens and connectors stop receiving `apple-health` and `iphone-health` rows until they are given the new scope. The owner session, environment tokens and background writers are unaffected.
- **Watch history panel**: the delete-import button is disabled while its request is pending, results are announced through an always-present status region, and a window with no watches says how many are held ("12 watches held, none in the last 30 days"). The time estimate shows its range plainly once video lengths are known.
- **Agents reading status no longer count as the owner seeing a check-in**: `status` peeks at the open check-in without marking it shown (so it cannot push the pulse toward a lapse), and its attention count now includes an open check-in and a due catch-up, matching `rhen_attention`.
- **Quicker portal presses**: large JSON answers are gzipped for clients that accept it, commands go to the server one at a time in press order, and Start, Refresh the plan and "Woke at" disable only themselves while their own command runs instead of every button on the page.

## [0.1.0] - 2026-11-05

First public release.

### Added

- **Planning engine**: a deterministic library that turns areas, outcomes, projects, actions, deadlines, commitments, energy, places and equipment into one recommendation, a forecast of whether each project fits, and a plan for the day. The same inputs and clock give the same answer, with the reasoning attached.
- **Web portal**: Now, Day and Week, Plan, Inbox and Import, the weekly review, and a command palette (Ctrl K).
- **`rhen` command line and MCP server**: scripts and AI tools work the same data through the same validated commands, with changes recorded in an undo log you can review and reverse.
- **Outbound proxy and connection host**: the one place third-party credentials live; connections are add-on packages ([writing a connection](docs/architecture/writing-a-connection.md)).
- **Archive, cancel and restore**: one Archive or Cancel button per plan item with a ten-second Undo, a Review > Closed page that shows who closed each item and why and restores it, and a Now and Day line for what an agent closed in the last 24 hours.
- **Self-hosting**: PostgreSQL persistence with one baseline migration, a bundled database, verified daily backups (off until you turn them on), and Docker images for linux/amd64 and linux/arm64 that `docker compose up` builds from source (published images are planned). Start with `docker compose run --rm setup` and `docker compose up -d`.
- **OpenClaw plugin**: attached to the release as `openrhen-openclaw-plugin-<version>.tgz` with a `.sha256` and a build-provenance attestation ([install](integrations/openclaw-plugin/README.md)). The plugin has its own version number.

### Fixed

- **Calendar cancellations**: when a connected calendar or feed cancels an event, or an event disappears from it, OpenRhen now cancels the commitment (with its steps and safe prep actions) instead of deleting it. It shows in Review > Closed with the reason "Removed at source" and can be restored there; an event that comes back reopens it, and one you cancelled yourself is never reopened by an import. The close brake counts these cancellations, and an import preview says "Still cancelled by you" for an update to a commitment you cancelled.
- **Ending a recurring commitment**: ending the rule (or a calendar feed ending its series) now cancels its future dates (with their steps and the prep actions that are safe to cancel) instead of deleting them. They show in Review > Closed with the reason "Recurrence ended" and who ended it, the planner never prunes or reopens them, and setting the rule active again brings back exactly the dates that end closed (with their steps) while a date you cancelled yourself stays cancelled. One date can also be restored on its own, and the planner keeps it. An agent's save can no longer delete deliverable steps: leaving a step out is refused with the exact cancel or archive call, and your own saves are unchanged.
- **Closing a finished step**: archiving a done deliverable step no longer breaks the state read with a validation error. The step comes back as archived, is left out of the deliverable's progress count and never holds up completion, and re-saving the deliverable keeps a closed step as it is without letting a save close one.

### Known limits

- Pre-1.0: screens, commands and schemas can change between minor versions, and this file says when.
- Built for one person per installation; there are no user accounts or sharing.
- Owner sign-in is off by default and is only safe on `127.0.0.1`. Lock the API down before exposing it ([locking down](docs/operations/locking-down.md)).
- No telemetry, and no hosted service: you run it yourself.
